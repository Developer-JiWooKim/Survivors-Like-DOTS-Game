## 2026-09-17 (4) — [M1→M2 선행] 투사체 충돌·최근접 탐색을 해시 조회로 교체 ✅

**커밋** `(미커밋)` — 교체 전 코드는 `9ac3060` | **관련 이슈** 없음

> 상태: 코드 + 컴파일 + 사용자 동작 확인 + 평상 프레임 측정 완료. PlayerLoop 1.88 → 1.5~1.8 ms (소폭, 오차 범위와 겹침).

### 한 일

| 파일 | 변경 |
|---|---|
| `Spatial/EnemySpatialHash.cs` | `MaxAgentRadius`(0.5) + `CellRangeFor(반경)` — 조회 반경에 따라 몇 칸 볼지 계산 |
| `Weapon/ProjectileHitSystem.cs` | 적 전체를 리스트 3 개(Entity·위치·반경)로 복사 후 전수 비교 → **투사체 주변 9 칸만 조회**. 복사 제거 |
| `Weapon/ShardFireSystem.cs` | `ToComponentDataArray` 로 적 전체 복사 후 전수 탐색 → **플레이어 셀부터 고리 모양으로 넓혀가는 탐색**, 사거리(18)까지만 |
| `Enemy/EnemyChaseSystem.cs` | 검사 범위 계산을 `CellRangeFor` 로 통일 |

### 왜 이렇게 했나

**1. 최근접 탐색 범위 = 무기 사거리** (사용자 결정)
- **대안**: 거리 무관하게 가장 가까운 적 (기존 규칙) — 주변이 비면 스폰 반경(~40)까지 수천 칸을 훑는다.
- **선택 이유**: 닿지 않을 적에게 탄을 낭비하지 않고, 탐색 비용 상한이 생긴다. **게임 규칙이 바뀐 것** — 사거리 안에 적이 없으면 쏘지 않고 대기.

**2. 고리 탐색의 조기 종료**
- 고리 r 을 다 본 뒤, 다음 고리의 셀은 원점에서 **최소 r × 셀 크기** 떨어져 있다 (원점은 중심 셀 안 어딘가).
  이미 그보다 가까운 적을 찾았으면 멈춘다. 적이 가까우면 1~2 고리로 끝난다.
- 고리는 테두리만 돈다 — 가운데 행은 양 끝 두 칸만.

**3. `MaxAgentRadius` 가 필요한 이유**
- 적은 **중심 좌표의 셀**에만 들어간다. 반경이 큰 적은 옆 칸에 중심이 있어도 닿을 수 있어서, 조회 반경 + 적 최대 반경만큼 칸을 봐야 누락이 없다.
- 이전 분리 코드는 "상대도 나와 같은 크기" 로 가정했는데, 세 조회(분리·충돌·탐색)를 이 상수 하나로 통일했다. M4 에서 Blob 스탯 최대치로 교체.

**4. 발사 시스템을 적 이동보다 앞으로 옮김** (순서 변경)
- 발사 시 메인 스레드에서 `LocalTransform` 을 읽고 쓴다. 이전 순서(이동 **뒤**)에서는 적 이동 잡이 끝날 때까지 기다리는 **동기화 지점**이 발사 프레임마다 생겼다.
- 이동 **앞**이면 기다릴 것은 해시 재구축뿐이고, 그건 조회에 어차피 필요하다. 탐색 대상도 해시 스냅샷(이동 전)이라 순서가 맞는다.

**5. 해시 스냅샷이 1 프레임 이르다는 점**
- 충돌 판정이 **이동 전** 적 위치를 본다. 적 이동량은 프레임당 약 0.04 u 로 판정 반경 합(0.4)의 10% — 무시.

### 성능 측정

| 항목 | Before (`9ac3060`, 전수 비교) | After | 조건 |
|---|---|---|---|
| FPS (프레임 ms) | 181.3 (5.52) | 341.1 (2.93) | 적 1,000, 오버레이 값 |
| Main | 5.48 ms | 2.92 ms | 오버레이 값 |
| **PlayerLoop** (프로파일러) | **1.88 ms** (평상 프레임 1 개) | **1.5 ~ 1.8 ms** (평상 프레임 여러 구간, 사용자 확인) | ← 비교 기준 |
| EditorLoop | 3.23 ms (59%) | 1.32 ms | 측정 조건이 달라짐 |
| Ents / Draw / SetPass / Tris | 1,076 / 12 / 10 / 2,700 | 1,076 / 12 / 10 / 3,160 | |

> **결론 — PlayerLoop 기준 약 0.1 ~ 0.4 ms (5 ~ 20%) 감소. 다만 오차 범위와 겹친다.**
> - Before 는 프레임 1 개 값이고 After 는 여러 구간의 범위라 엄밀한 비교가 아니다. "줄었을 가능성이 높다" 까지만 주장한다.
> - 차이가 작은 이유: 적 1,000 · 투사체 수 발 규모에선 **전수 비교 비용 자체가 원래 작았다** (M1 설계 시 예상한 대로). 해시의 이득은 적 수가 늘수록 커진다 → M2 1만 마리 벤치에서 다시 본다.
> - 오버레이의 Main·FPS 차이는 아래처럼 에디터 쪽 변화가 섞여 코드 효과로 쓰지 않는다.
>
> **(초기 해석 — After 프로파일러 스크린샷 기준)**
> - Main 은 5.48 → 2.92 ms (−2.56 ms) 로 줄었지만, 같은 기간 **EditorLoop 도 3.23 → 1.32 ms (−1.91 ms)** 로 줄었다.
>   에디터 쪽 변화(Profiler 창 배치·포커스 등)가 감소분의 대부분을 설명할 수 있어 코드 효과와 분리되지 않는다.
> - After 프로파일러 스크린샷은 **주기적 스파이크 프레임**(CPU 13.73 ms, 커서가 10.95 ms 스파이크 위)을 선택한 상태라 PlayerLoop 12.07 ms 는 평상 프레임 값이 아니다.
> - Tris 증가(2,700 → 3,160)는 화면 안 적이 더 많은 시점이라는 뜻 — 부하 조건이 약간 더 무거웠다.
> - **필요한 것**: 스파이크가 아닌 평상 프레임의 PlayerLoop, 가능하면 `ProjectileHitSystem` / `ShardFireSystem` 개별 ms.
>
> **동작 확인 (사용자)**: 교체 후 정상 동작.
>
> **주기적 스파이크 → 게임 코드 원인 아님 (조사 종료).** 스파이크 프레임을 펼친 결과 **EditorLoop 가 209.95 ms** 로 튀었고 PlayerLoop 는 평상 수준 (사용자 확인).
> 에디터 자체 작업이라 빌드에는 없을 것으로 보지만, **빌드 실측 때 스파이크가 사라지는지 한 번 확인**한다.
>
> (조사 전 의심했던 후보 —
> PerfOverlay 의 `OnGUI`(IMGUI 매 프레임 할당) → GC, 0.25 초마다 `UniversalQuery.CalculateEntityCount()` 가 만드는 **전 잡 동기화 지점**.
> → 둘 다 스파이크의 원인은 아니었다. 다만 `CalculateEntityCount()` 의 4 Hz 동기화 지점과 PlayerLoop GC Alloc 1.5 KB 는 **그 자체로 남아 있는 사실**이라, 빌드 측정 때 영향이 보이면 다룬다.)

> **측정 환경**: 에디터 플레이 모드 / 사용자 측정 / **Profiler 창 열린 상태** / 적이 아직 몰려오는 중인 시점
>
> - Profiler 창을 열면 EditorLoop 가 크게 늘어 Main·FPS 가 왜곡된다. **게임 코드 비교는 PlayerLoop 로 한다.**
>   적 500 측정(2.27 ms, Profiler 없음)과 비교 불가한 이유이기도 하다.
> - PlayerLoop 에 **GC Alloc 1.5 KB** 가 보인다. 매 프레임이라면 주기적 스파이크 원인 후보 (PerfOverlay 문자열 의심) — 별도 확인 필요.
> - 적 밀집도가 시간에 따라 변하므로 After 도 **비슷한 경과 시점**에 잰다.

## 2026-09-17 (3) — [M1→M2 선행] 적 공간 해시 + 적끼리 분리 ✅

**커밋** `(미커밋)` | **관련 이슈** 없음

> 상태: 코드 + 컴파일 + 사용자 플레이 확인 완료 (적 500).
> **마일스톤 순서 변경**: 사용자 요청으로 대시를 보류하고, M2 핵심 작업인 공간 해시·분리를 M1 도중에 앞당겼다.
> M1 의 나머지(XP·레벨업)는 그대로 남아 있다.

### 요청
"적이 몰려올 때 겹치지 않게 서로 피하게 하자. 전체를 읽으면 연산량이 감당 안 되니 자기 주변만 검사하자." (사용자)

### 한 일

| 파일 | 역할 |
|---|---|
| `Spatial/AgentRef.cs` | 해시 한 칸의 값 — 엔티티, 위치 **스냅샷**, 반경 |
| `Spatial/EnemySpatialHash.cs` | 싱글턴: `NativeParallelMultiHashMap<int, AgentRef>` + 빌드/조회 잡 핸들. 셀 크기 1.0 (기획서 8.3), 셀 좌표 → 키 헬퍼 |
| `Spatial/BuildEnemySpatialHashSystem.cs` | 매 프레임 비우고 살아있는 적을 **병렬로** 다시 채움 (기획서 8.2 의 6번) |
| `Enemy/EnemySeparation.cs` | 분리 설정 싱글턴: 강도 1.5, 이웃 검사 상한 16 |
| `Enemy/EnemySpawnerAuthoring.cs` (수정) | 분리 설정을 스포너에 베이킹 (씬 작업 불필요) |
| `Enemy/EnemyChaseSystem.cs` (재작성) | 추격 방향 + 이웃 밀어내기 합성. 자기 셀 ± 범위만 조회 |

**순서**: `EnemyRespawn → BuildEnemySpatialHash → (PlayerMove) → EnemyChase → ...`

**알고리즘** (적 1 마리 기준)
```
chase = 플레이어 방향 (길이 1, 도착 직전엔 남은 거리만큼 축소)
push  = Σ (나 - 이웃) 단위벡터 × (1 - 거리 / (내 반경 + 이웃 반경))   ← 겹친 이웃만, 최대 16 마리
dir   = chase + push × 1.5,  길이 1 로 상한
이동  = dir × 속도 × dt
```

### 왜 이렇게 했나

**1. 공간 해시 = MultiHashMap 먼저** (사용자 결정)

- **대안**: 카운팅 소트 그리드 (기획서의 최적화 2단계). 캐시 지역성이 좋아 2~3 배 빠르다고 예상되지만, 고정 월드 범위가 필요하고 코드가 복잡하다.
- **선택 이유**: 병렬 쓰기가 쉬워 코드가 단순. 나중에 그리드로 바꿀 때 **before/after 측정**이 면접 소재가 된다.
- 셀 키는 `math.hash(int2)`. 서로 다른 셀이 같은 키로 충돌할 수 있지만 조회 쪽이 거리로 다시 걸러 정확성에 영향 없다.
- `(int)` 캐스트가 아니라 `floor` 로 셀을 구한다 — `(int)(-0.5) == (int)(0.5) == 0` 이라 원점 주변 셀이 두 배 크기가 된다.

**2. 분리 = 밀어내는 힘 (보이드 separation)** (사용자 결정)

- **대안 A — 겹침 위치 보정**: 겹침은 확실히 없어지지만 상호 보정이라 병렬화하려면 스냅샷 + 반씩 밀기가 필요하고, 밀집 구간에서 떨림이 생기기 쉽다.
- **대안 B — 힘 + 깊은 겹침만 보정**: 품질은 가장 좋지만 조정할 수치가 늘어난다.
- **선택 이유**: 움직임이 부드럽고 **병렬화가 그대로 안전**하다.
- **알려진 한계**: 플레이어 주변처럼 사방에서 추격 힘이 모이면 약간 겹칠 수 있다 — 강도(1.5)로 조절.

**3. 병렬 안전성 — 스냅샷을 해시에 복사**

- 이웃 위치를 `ComponentLookup<LocalTransform>` 으로 읽으면, 같은 잡이 자기 `LocalTransform` 에 쓰는 것과 충돌해 `ScheduleParallel` 이 불가능하다.
- 해시에 위치를 복사해 두면 "이웃은 해시에서 읽고, 쓰기는 자기 것만" → 2026-09-16 에 기록한 "분리를 넣는 순간 병렬화가 깨진다" 는 우려를 이 방식으로 피했다.
- 대가: 이웃의 **이번 프레임 이동을 모른 채** 피한다 (1 프레임 늦은 정보). 체감 불가.

**4. 해시 컨테이너의 잡 의존성을 직접 관리**

- 컨테이너가 컴포넌트 안에 있어 ECS 자동 의존성 추적이 닿지 않는다. `DamageEventBus` 와 같은 패턴으로 핸들 두 개를 둔다.
  - `BuildHandle` — 추격 잡이 재구축 완료 뒤에 돌도록
  - `ReadersHandle` — 다음 프레임 `Clear()` 전에 지난 프레임 조회 잡을 끝내도록
- 병렬 쓰기는 용량을 못 늘려서 `Capacity` 를 미리 확보. 개수는 `CalculateEntityCountWithoutFiltering()` (풀 전체 = 상한) — 필터를 쓰면 enabled 비트 때문에 동기화 지점이 생긴다.

**5. 세부 결정**

- **분리 반경 = 두 적의 `HitRadius` 합** — 별도 수치를 두지 않았다. 기획서 `AgentRef` 에 `Radius` 가 있는 이유도 이것.
- **검사 셀 범위를 계산** (`ceil(내 반경 × 2 / 셀 크기)`) — 반경을 키워 셀보다 커져도 이웃을 놓치지 않게. 현재 값(0.25)에서는 ±1 = 9 칸.
  "상대 반경도 나와 같다" 는 M1 가정이 들어 있다 — 적 크기가 달라지는 M4 에서 재검토.
- **이웃 16 마리 상한** — 밀집 구간 최악 비용을 자른다. 가까운 순이 아니라 발견 순이라 정밀도는 약간 희생.
- **완전히 같은 위치** — 재스폰 직후·플레이어 중심에서 실제로 생긴다. 두 적이 **반대 방향**을 받도록 엔티티 쌍의 해시로 각도를 정하고 인덱스 크기로 부호를 나눴다. 각자 난수를 쓰면 같은 쪽으로 밀려 계속 붙어 있을 수 있다.
- **최종 방향 길이 1 상한** — 밀리는 적이 자기 속도보다 빨리 튀어나가지 않게.
- **플레이어는 밀지 않는다** — 적끼리만 피한다. 적은 여전히 플레이어 중심을 향하므로, 플레이어 주변에 원형으로 뭉친다.

### 왜 이렇게 했나

**1. 적 판정 반경 = 보이는 크기 (0.25)** (사용자 결정)

- 스케일 0.5 + 판정 0.5 조합을 검토: 판정이 보이는 크기의 2 배라, 플레이어 피격이 0.5 + 0.4 = **0.9** 거리에서 들어와 "안 닿았는데 맞는" 느낌이 된다.
- **대안**: 투사체용(0.5)과 접촉용(0.25) 반경 분리 — 플레이어에게 유리한 관대한 판정이지만 적당 4 byte 증가.
- **선택**: 기획서 8.3 값(0.25)으로 통일. 가장 단순하고 시각과 일치.

**2. 사망 시 정지 = 그룹 게이트** (사용자 결정 — 기획서 8.2 의 2번 RunStateSystem 에 해당)

- **대안 A — `Time.timeScale = 0`**: 한 줄이지만 시스템·잡은 계속 돌고(스케줄 비용 그대로), dt 를 안 쓰는 로직(재스폰)은 멈추지 않고, 레벨업 UI 연출도 멈춰서 unscaled time 을 써야 한다.
- **대안 B — 로그만**: 정지 설계를 레벨업 작업으로 미룸.
- **선택 이유**: 레벨업 일시정지(기획서 7.1)가 **같은 장치를 재사용**한다 (`RunPhase.Paused`). 그룹을 건너뛰면 잡 비용까지 0, 변환·렌더는 계속 돌아 화면이 유지된다.
- **비용**: 기존 시스템 8 개의 그룹 변경. 그룹은 class(`ComponentSystemGroup`)여야 해서 managed — 프레임당 분기 1 회라 무시.
- **부수 효과**: 게임플레이 시스템이 `TransformSystemGroup` **보다 먼저** 돌도록 명시됐다. 이전엔 순서 미지정이라, 이동한 위치가 렌더 행렬(LocalToWorld)에 1 프레임 늦게 반영됐을 가능성이 있었다.

**3. 접촉 피해는 적 N × 플레이어 1 → 공간 해시 불필요**

- 투사체 충돌(N×M)과 달리 대상이 1 명이라 O(N). 1만 마리에서도 거리 비교 1만 번이라 병렬 잡으로 충분 — **M2 에서도 교체 대상이 아니다.**
- 이벤트를 합산하지 않고 적마다 하나씩 쓴다: 나중에 "누가 때렸나"(피격 연출·속성 피해) 정보가 필요. 붙어있는 적 수백 마리여도 적용 비용 무시 수준.
- 피해량 = `초당 피해 × dt` — 프레임레이트와 무관하게 초당 피해가 일정.

**4. 플레이어 위치는 잡 안에서 룩업으로 읽는다**

- 메인 스레드에서 `GetComponent<LocalTransform>(player)` 를 하면, 직전에 예약된 적 이동 잡(LocalTransform 쓰기)을 **매 프레임 기다리는** 동기화 지점이 된다 (ISSUE-006 과 같은 종류의 함정).

**5. 사망 판정은 그룹 맨 앞에서 "지난 프레임" 체력으로**

- 피해 적용 직후에 메인 스레드에서 읽으면 이번 프레임 잡 체인 전체(이동→충돌→적용)를 매 프레임 기다린다.

**3. `Active` 만 끄면 렌더링이 안 꺼진다 → `MaterialMeshInfo` 도 함께 토글**

- Entities Graphics 는 우리 `Active` 태그를 모른다. 패키지 소스(`RenderMeshArray.cs:38`)에서
  **`MaterialMeshInfo : IComponentData, IEnableableComponent`** 임을 확인 → 구조적 변경 없이 렌더만 끌 수 있다.

**4. `EnabledRefRW` 를 쓰는 잡은 쿼리를 직접 만들어 넘김**

- `IJobEntity` 파라미터에 `EnabledRefRW<T>` 가 있을 때 기본 쿼리가 "켜진 것만" 인지 "있기만 하면" 인지를 **코드젠에 맡기지 않고** 명시.

**5. 데미지 버스 — 스트림마다 적용 잡 하나씩 직렬 체인**

- 처음 설계: 등록된 스트림들을 `NativeArray<NativeStream>` 으로 잡 하나에 넘기기.
  → **컨테이너 안의 컨테이너는 잡 안전 검사에서 거부된다**는 걸 떠올리고 작성 중에 폐기.

- **선택 이유 (결정적)**: **지형 시스템**. 기획서상 플레이어는 연소 타일에서 피해를 받고,
  빙판에서 이동속도가 바뀌고, 균열에서 속도가 변한다. 이게 전부 타일 그리드 잡 안에서 일어나는데
  플레이어만 GameObject 면 **이 판정을 플레이어용으로 한 번 더 따로 짜야 한다.**
  부차적으로, 하이브리드는 BRG 엔티티와 SpriteRenderer 라는 **렌더 경로 2개**가 생겨
  둘 사이의 앞뒤 정렬(렌더 큐 vs Sorting Layer)이 까다로워진다.
- **포기한 것**: `Animator` 와 애니메이션 편집 워크플로우. 플레이어 애니메이션을 UV 프레임 인덱스로
  직접 계산해야 한다. 뱀서라이크 플레이어는 보통 idle/walk 몇 프레임 + 좌우 반전 + 피격 플래시라
  감당 가능하다고 판단.
- **탈출구**: Entities 에 `Unity.Entities.Hybrid.HybridComponents` (Companion GameObject) 가 있다.
  애니메이션이 정말 복잡해지면 **플레이어 1개에만** GameObject 를 붙여 `Animator` 를 쓸 수 있다.
  1만 개에 쓰면 망하지만 1개는 비용이 무의미하다. **되돌리기 어려운 결정이 아니다.**

**2. 입력만 SystemBase, 나머지는 전부 ISystem + Burst**

- **선택 이유**: `InputActionAsset` / `InputAction` 은 매니지드 클래스라 Burst ISystem 에서 다룰 수 없다.
  매니지드 경계를 **이 시스템 하나로 격리**하고, 읽은 값을 싱글턴 컴포넌트에 써두면
  이후 모든 게임플레이 시스템은 Burst 로 컴파일된 채 그 값을 읽는다.
  플레이어를 엔티티로 둔 이유(동기화 경계 최소화)가 실제 구조로 구현된 지점.

**3. 새 Input Actions 를 만들지 않고 기존 `Player/Move` 재사용**

- 프로젝트에 `InputSystem_Actions.inputactions` 가 이미 전역 액션으로 설정돼 있었고
  `Player/Move` 가 Vector2 + WASD 로 구성돼 있어 그대로 썼다. API 존재 여부(`InputSystem.actions`,
  `InputActionAsset.FindAction`)는 패키지 소스에서 직접 확인한 뒤 사용.

**4. 대각선 정규화를 입력 단계에서**

- WASD 는 (1,1) 이 들어와 길이가 √2 가 된다. 정규화하지 않으면 대각선이 41% 빠르다.
- **길이가 1 을 넘을 때만** 정규화한다. 게임패드 아날로그 스틱은 살짝 기울인 상태의 길이가
  1 미만인데, 무조건 정규화하면 미세 조작이 전부 최대 속도가 되어버린다.

**5. 플레이어를 싱글턴이 아니라 Query 로 순회**

- 플레이어는 1 개지만 `SystemAPI.Query` 로 돈다. 싱글턴으로 강제하면 나중에 구조를 바꿔야 하고,
  1 개짜리 순회는 비용이 사실상 0 이다.

**6. 카메라는 MonoBehaviour 유지**

- 카메라는 Unity 매니지드 오브젝트라 어차피 GameObject 다. 중요한 건 이게 **ECS 를 읽기만 하는
  단방향**이라는 점 — 양방향 동기화 버그가 생길 여지가 없어 "플레이어를 엔티티로" 결정과 충돌하지 않는다.
- `LateUpdate` 에서 갱신한다. 시뮬레이션이 플레이어를 움직인 뒤 따라가야 한 프레임 밀리지 않는다.
- 추적 보간은 `1 - exp(-k * dt)` 를 쓴다. `Lerp(a, b, k * dt)` 는 프레임률에 따라 추적 속도가 달라진다.

### 왜 이렇게 했나

**1. 차별화 축을 "지형 시뮬레이션"에 집중**

- **선택**: 지형을 상태를 가진 타일 그리드 시뮬레이션으로 만들고, 무기가 지형을 조작 → 지형이 다시 무기를 증폭시키는 구조
- **대안**: (a) 무기 진화만 파기 (원작 답습) (b) 지형을 단순 시각 연출로만 처리
- **선택 이유**: 무기 진화와 지형을 각각 독립적으로 넣으면 둘 다 평범해진다. 둘을 엮어서 **킬러 콤보를 전부 "무기 2개 + 지형"의 3항 조합**으로 설계하면, 무기만 모아선 강해질 수 없는 고유한 빌드 설계 재미가 생긴다. 동시에 수십만 타일 시뮬레이션은 **DOTS를 쓰는 기술적 명분 그 자체**라 포트폴리오 관점에서도 1만 유닛보다 설명거리가 많다.
- **포기한 것**: 구현 범위가 크게 늘어남 (타일 그리드 + 상태 전파 Job + 지형 렌더링이 통째로 추가). 지형이 재미없으면 기획의 절반이 무너지는 리스크를 안음 → M3에서 최소 3개 무기로 조기 검증하는 걸로 완화.

**2. 목표 밀도 1만 + M2를 게이트로 설정**

- **선택**: M2(공간 해시·풀링·인스턴싱 렌더로 적 1만 @60fps)를 통과하기 전엔 M3 이후 콘텐츠를 만들지 않는다
- **선택 이유**: 성능 뼈대(풀링, 공간 해시, 단일 아키타입)는 **나중에 끼워넣는 비용이 압도적으로 크다.** 콘텐츠를 먼저 쌓은 뒤 성능이 안 나오면 전부 다시 써야 한다.
- **포기한 것**: 초반에 눈에 보이는 결과물이 적어 동기 부여가 떨어짐 → M1에서 적 1,000 규모의 플레이 가능한 루프를 먼저 만들어 완화.
- **분기 계획**: M2 미달 시 목표 밀도를 3,000으로 낮추고 기획 재조정 (기획서 10장에 명시)

**3. Unity Physics 미사용 결정**

- **선택**: 물리 패키지를 설치하지 않고 공간 해시 기반 원-원 겹침 판정을 직접 구현
- **대안**: Unity Physics (`com.unity.physics`) 사용
- **선택 이유**: 2D 원-원 판정만 필요한데 Unity Physics는 월드 빌드 + 브로드페이즈 + 내로우페이즈 전체 파이프라인 비용을 지불해야 한다. 1만 유닛에서 감당이 안 될 것으로 판단.
- **포기한 것**: 검증된 물리 구현을 버리고 직접 만들게 됨 → 버그 리스크. 단 판정 종류가 원-원 하나뿐이라 감당 가능한 범위로 봄.
- **⚠ 미검증**: 이건 **아직 실측으로 확인한 게 아니라 판단**이다. M2에서 자체 구현 공간 해시의 실제 수치를 측정해 이 결정이 옳았는지 검증 필요.

**4. 적을 단일 아키타입으로 설계**

- **선택**: 적 6종 전부 하나의 아키타입. 차이는 `EnemyTypeId(byte)` + Blob 스탯 테이블로 분기
- **대안**: 적 타입별로 다른 컴포넌트 조합 = 다른 아키타입
- **선택 이유**: ECS는 아키타입 단위로 청크가 나뉜다. 타입별로 아키타입을 나누면 청크가 파편화되어 순회 시 캐시 효율이 무너지고, 청크 하나가 절반만 차는 상황이 속출한다.
- **포기한 것**: 타입별 고유 컴포넌트를 못 쓰므로 모든 적이 안 쓰는 필드까지 들고 다님 (메모리 낭비). 대신 컴포넌트를 작게 유지(적 1개당 ≤64byte 목표)해서 상쇄.
