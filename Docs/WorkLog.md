## 2026-09-17 (10) — [M2] 벤치마크 모드 + **적 10,000 게이트 측정 (에디터 통과)** ✅

**커밋** `(미커밋)` | **관련 이슈** 없음

> 상태: 완료. **적 10,000 @ 203 FPS (에디터)** — M2 게이트 에디터 기준 통과. 빌드 실측은 남음.

### 문제
적 1 만 벤치에서 두 가지가 측정을 방해한다.
- 플레이어가 곧 죽는다 → 게임오버로 `GameplaySystemGroup` 이 멈춰 측정 무의미
- 적을 많이 잡아 레벨업 창이 계속 뜬다 → 일시정지로 측정 구간이 끊김

### 결정 (사용자 — 추천안)
**벤치마크 모드**를 추가하고, **고정 목표 수(`FixedTarget > 0`)와 한 옵션으로 묶는다.**
- **대안**: 인스펙터에서 플레이어 체력을 1e9 로 — 코드 변경은 없지만 레벨업 창이 계속 떠서 안정 구간을 잡기 어렵다.
- 한 옵션으로 묶은 이유: "적 수 고정" 과 "무적 / 레벨업 없음" 은 항상 같이 필요하다. 따로 두면 한쪽만 켜 두는 실수가 생긴다.
- **전투·사망·젬·재스폰은 그대로 돈다** → 실제 플레이에 가까운 부하. (피해 0 같은 방식은 사망·재스폰 경로가 빠져 부하가 달라진다.)

### 한 일
| 파일 | 변경 |
|---|---|
| `Enemy/EnemySpawner.cs` | `SpawnDirector.IsBenchmark` (= `FixedTarget > 0`) |
| `Player/PlayerDeathSystem.cs` | 벤치마크면 체력 바닥 시 최대치로 복구 (게임오버 안 함) |
| `Leveling/LevelUpSystem.cs` | 벤치마크면 레벨업 판정 건너뜀 (경험치만 쌓임) |
| `Diagnostics/PerfOverlay.cs` | `[BENCH] god mode, no level-up` 표시 — 켜 둔 채 플레이하는 실수 방지. IMGUI 기본 폰트의 한글 글리프 문제로 영어 |

### 성능 측정 — M2 게이트 (적 10,000 고정)

| 항목 | 적 1,000 (M1 게이트, (9)) | **적 10,000 (M2 게이트)** |
|---|---|---|
| 모드 | 고정 1,000 (벤치마크 모드 도입 전) | `[BENCH]` 무적 · 레벨업 없음 |
| 생존/목표 | 1,000 | **10,000 / 10,000** |
| FPS (프레임) | 94 (10.6 ms) | **203.0 (4.91 ms)** |
| Main | 5.66 ms | 4.76 ms |
| PlayerLoop (프로파일러) | 1.8 ~ 2.0 ms | 2 ~ 3.3 ms |

> **측정 환경**: 에디터 플레이 모드 / 사용자 측정 / 빌드 실측 아님. Tris·Safety Checks 상태는 미기록.
>
> **게이트 판정: 적 10,000 에서 203 FPS ≥ 60 → 에디터 기준 통과.**
>
> **해석**
> - 적이 10 배로 늘었는데 PlayerLoop 는 약 1.1 ~ 1.7 배. 이동·분리·충돌이 **워커 스레드의 병렬 잡**이라 메인 스레드 시간에 거의 잡히지 않는다.
>   → **PlayerLoop 는 메인 스레드 시간일 뿐** 워커 부하를 포함하지 않는다. 게이트 판단은 프레임 시간(FPS)으로 한다.
> - **이상점**: 적 1,000 측정(94 FPS)이 적 10,000(203 FPS)보다 느리다. 1,000 측정에서만 "프레임 − Main ≈ 5 ms" 가 있었고 이번엔 거의 없다 (4.91 vs 4.76).
>   → 1,000 측정 때 **코드 밖 요인**(에디터 창 상태 · Game 뷰 · VSync 등)이 끼었을 가능성이 높다. 원인은 측정하지 않았으므로 단정하지 않는다.
>   → 이 때문에 두 측정 사이의 비교는 하지 않는다.
> - **남은 확인**: 이 값은 적이 화면에 얼마나 그려졌는지(Tris)가 빠져 있다. **렌더 쪽 절반은 빌드 실측에서 확정**한다 (CLAUDE.md 3.3).

### 검증
- 컴파일 성공 / 테스트 15/15
- **플레이 확인 (사용자)**: 벤치마크 모드 동작 (`[BENCH]` 표시, 10,000/10,000 유지)

**2. 한 프레임 여러 번 발사 + 상한 4**
- 기존 구조(프레임당 1 회)는 발사 간격이 프레임 시간보다 짧아지는 순간 **연사 속도가 FPS 에 묶인다** (60 FPS 면 초당 최대 60 회).
- 상한이 없으면 긴 프레임(로딩·에디터 멈춤) 뒤 수십 회를 몰아 쏜다. 상한에 걸려 밀린 발사는 **버린다** — 남기면 다음 프레임에도 계속 몰아 쏜다.
- 타겟은 프레임에 한 번만 찾는다 (같은 프레임의 발사들은 대상이 같다).

**3. 가까운 T 마리 탐색 — 정렬 삽입 + 고리 조기 종료**
- T ≤ 16 이라 힙보다 삽입 정렬이 싸다. `FixedList` 두 개(위치·거리)를 나란히 유지.
- 종료 조건: T 마리를 모았고, T 번째 거리가 다음 고리의 최소 거리(ring × 셀) 이하.

**4. 관통 — 명중 기록을 컴포넌트 안에 `FixedList128Bytes<Entity>`**
- **대안**: `DynamicBuffer<Entity>` — 버퍼 헤더 + 넘치면 힙 할당. / 기록 없이 관통 — 겹쳐 있는 동안 같은 적을 매 프레임 때린다.
- 15 칸이면 관통 상한 10 + 직격을 넉넉히 덮는다. 가득 차면 가장 오래된 기록부터 버린다.
- **풀 재사용 시 기록을 반드시 비운다** (발사 시 `HitHistory = default`). 안 비우면 지난 생애에 맞힌 적을 이번 생애에 못 맞힌다.
- 한 프레임에 한 마리만 맞힌다 — 탄이 프레임당 약 0.2 u 이동해 적 지름(0.5)보다 작으므로, 붙어 있는 적도 다음 프레임에 차례로 맞는다.
- 걸린 것: `FixedList.Contains` 는 `ref this` 확장이라 `in` 매개변수로 넘기면 CS8329. `ref` 로 변경.

**5. 폭발 — 직격 대상 제외, 적 위치 중심**
- 직격 대상은 직격 피해만 (폭발 피해 50% 를 "주변 피해" 로 명확히).
- 중심은 맞은 적의 위치 — 적 중심에서 퍼지는 게 시각적으로 자연스럽다 (폭발 연출은 M3).
- 반경 상한 3.0 — 조회 셀이 반경의 제곱으로 늘어난다 (3.0 → 9×9 = 81 칸).

**6. 최대치 도달 선택지 제외**
- 수치 강화 5 종은 상한이 없어 항상 후보 → 후보가 3 개 미만이 되는 일은 없다.

### 왜 이렇게 했나

**1. 최근접 탐색 범위 = 무기 사거리** (사용자 결정)
- **대안**: 거리 무관하게 가장 가까운 적 (기존 규칙) — 주변이 비면 스폰 반경(~40)까지 수천 칸을 훑는다.
- **선택 이유**: 닿지 않을 적에게 탄을 낭비하지 않고, 탐색 비용 상한이 생긴다. **게임 규칙이 바뀐 것** — 사거리 안에 적이 없으면 쏘지 않고 대기.

**2. 고리 탐색의 조기 종료**
- 고리 r 을 다 본 뒤, 다음 고리의 셀은 원점에서 **최소 r × 셀 크기** 떨어져 있다 (원점은 중심 셀 안 어딘가).
  이미 그보다 가까운 적을 찾았으면 멈춘다. 적이 가까우면 1~2 고리로 끝난다.
- 고리는 테두리만 돈다 — 가운데 행은 양 끝 두 칸만.

**3. `MaxAgentRadius` 가 필요한 이유**
- 적은 **중심 좌표의 셀**에만 들어간다. 반경이 큰 적은 옆 칸에 중심이 있어도 닿을 수 있어서, 조회 반경 + 적 최대 반경만큼 칸을 봐야 누락이 없다.
- 이전 분리 코드는 "상대도 나와 같은 크기" 로 가정했는데, 세 조회(분리·충돌·탐색)를 이 상수 하나로 통일했다. M4 에서 Blob 스탯 최대치로 교체.

**4. 발사 시스템을 적 이동보다 앞으로 옮김** (순서 변경)
- 발사 시 메인 스레드에서 `LocalTransform` 을 읽고 쓴다. 이전 순서(이동 **뒤**)에서는 적 이동 잡이 끝날 때까지 기다리는 **동기화 지점**이 발사 프레임마다 생겼다.
- 이동 **앞**이면 기다릴 것은 해시 재구축뿐이고, 그건 조회에 어차피 필요하다. 탐색 대상도 해시 스냅샷(이동 전)이라 순서가 맞는다.

**5. 해시 스냅샷이 1 프레임 이르다는 점**
- 충돌 판정이 **이동 전** 적 위치를 본다. 적 이동량은 프레임당 약 0.04 u 로 판정 반경 합(0.4)의 10% — 무시.

### 왜 이렇게 했나

**1. 공간 해시 = MultiHashMap 먼저** (사용자 결정)

- **대안**: 카운팅 소트 그리드 (기획서의 최적화 2단계). 캐시 지역성이 좋아 2~3 배 빠르다고 예상되지만, 고정 월드 범위가 필요하고 코드가 복잡하다.
- **선택 이유**: 병렬 쓰기가 쉬워 코드가 단순. 나중에 그리드로 바꿀 때 **before/after 측정**이 면접 소재가 된다.
- 셀 키는 `math.hash(int2)`. 서로 다른 셀이 같은 키로 충돌할 수 있지만 조회 쪽이 거리로 다시 걸러 정확성에 영향 없다.
- `(int)` 캐스트가 아니라 `floor` 로 셀을 구한다 — `(int)(-0.5) == (int)(0.5) == 0` 이라 원점 주변 셀이 두 배 크기가 된다.

**2. 분리 = 밀어내는 힘 (보이드 separation)** (사용자 결정)

- **대안 A — 겹침 위치 보정**: 겹침은 확실히 없어지지만 상호 보정이라 병렬화하려면 스냅샷 + 반씩 밀기가 필요하고, 밀집 구간에서 떨림이 생기기 쉽다.
- **대안 B — 힘 + 깊은 겹침만 보정**: 품질은 가장 좋지만 조정할 수치가 늘어난다.
- **선택 이유**: 움직임이 부드럽고 **병렬화가 그대로 안전**하다.
- **알려진 한계**: 플레이어 주변처럼 사방에서 추격 힘이 모이면 약간 겹칠 수 있다 — 강도(1.5)로 조절.

**3. 병렬 안전성 — 스냅샷을 해시에 복사**

- 이웃 위치를 `ComponentLookup<LocalTransform>` 으로 읽으면, 같은 잡이 자기 `LocalTransform` 에 쓰는 것과 충돌해 `ScheduleParallel` 이 불가능하다.

- 대가: 이웃의 **이번 프레임 이동을 모른 채** 피한다 (1 프레임 늦은 정보). 체감 불가.

**4. 해시 컨테이너의 잡 의존성을 직접 관리**

**2. 사망 시 정지 = 그룹 게이트** (사용자 결정 — 기획서 8.2 의 2번 RunStateSystem 에 해당)

- **대안 A — `Time.timeScale = 0`**: 한 줄이지만 시스템·잡은 계속 돌고(스케줄 비용 그대로), dt 를 안 쓰는 로직(재스폰)은 멈추지 않고, 레벨업 UI 연출도 멈춰서 unscaled time 을 써야 한다.
- **대안 B — 로그만**: 정지 설계를 레벨업 작업으로 미룸.
- **선택 이유**: 레벨업 일시정지(기획서 7.1)가 **같은 장치를 재사용**한다 (`RunPhase.Paused`). 그룹을 건너뛰면 잡 비용까지 0, 변환·렌더는 계속 돌아 화면이 유지된다.
- **비용**: 기존 시스템 8 개의 그룹 변경. 그룹은 class(`ComponentSystemGroup`)여야 해서 managed — 프레임당 분기 1 회라 무시.
- **부수 효과**: 게임플레이 시스템이 `TransformSystemGroup` **보다 먼저** 돌도록 명시됐다. 이전엔 순서 미지정이라, 이동한 위치가 렌더 행렬(LocalToWorld)에 1 프레임 늦게 반영됐을 가능성이 있었다.

**3. 접촉 피해는 적 N × 플레이어 1 → 공간 해시 불필요**

- 투사체 충돌(N×M)과 달리 대상이 1 명이라 O(N). 1만 마리에서도 거리 비교 1만 번이라 병렬 잡으로 충분 — **M2 에서도 교체 대상이 아니다.**
- 이벤트를 합산하지 않고 적마다 하나씩 쓴다: 나중에 "누가 때렸나"(피격 연출·속성 피해) 정보가 필요. 붙어있는 적 수백 마리여도 적용 비용 무시 수준.
- 피해량 = `초당 피해 × dt` — 프레임레이트와 무관하게 초당 피해가 일정.

**4. 플레이어 위치는 잡 안에서 룩업으로 읽는다**

- 메인 스레드에서 `GetComponent<LocalTransform>(player)` 를 하면, 직전에 예약된 적 이동 잡(LocalTransform 쓰기)을 **매 프레임 기다리는** 동기화 지점이 된다 (ISSUE-006 과 같은 종류의 함정).
- `[ReadOnly] ComponentLookup<LocalTransform>` 으로 잡 안에서 읽고, 청크 시작 시 한 번만 조회해 캐시.

**5. 사망 판정은 그룹 맨 앞에서 "지난 프레임" 체력으로**

- 피해 적용 직후에 메인 스레드에서 읽으면 이번 프레임 잡 체인 전체(이동→충돌→적용)를 매 프레임 기다린다.
- 프레임 시작 시점엔 그 잡들이 대부분 끝나 있어 대기가 거의 없다. 대가는 **판정 1 프레임 지연** — 체감 불가.

**1. 최근접 탐색·충돌은 전수 비교, 결과는 스트림으로** (사용자 결정)

- **(b) 를 버린 이유**: 병렬 잡 두 개가 같은 적의 `Health` 를 쓰면 레이스. M2 에서 어차피 갈아엎어야 한다.

**2. 투사체·적 모두 enableable 풀링** (사용자 결정 — 추천안(M1 은 ECB 생성/파괴)과 다르게 감)

- **대안**: (a) M1 은 ECB Instantiate/Destroy, M2 에서 풀링 (b) 투사체만 풀링
- **선택 이유**: 기획서 8.4 의 최종 구조를 처음부터 따른다. 나중에 생명주기를 통째로 갈아엎는 비용을 피함.
- **포기한 것**: "구조적 변경 비용 before/after" 측정 기회. 그리고 M1 코드량 증가.

**3. `Active` 만 끄면 렌더링이 안 꺼진다 → `MaterialMeshInfo` 도 함께 토글**

- Entities Graphics 는 우리 `Active` 태그를 모른다. 패키지 소스(`RenderMeshArray.cs:38`)에서
  **`MaterialMeshInfo : IComponentData, IEnableableComponent`** 임을 확인 → 구조적 변경 없이 렌더만 끌 수 있다.
- **대안**: `DisableRendering` 태그 추가/제거 — 구조적 변경이라 원칙 위반. / 비활성 엔티티를 화면 밖으로 순간이동 — 컬링·판정 쪽에 암묵적 가정이 생김.
- 둘을 **반드시 함께** 바꿔야 해서 메인 스레드는 `PoolUtility.SetAlive` 한 곳, 잡은 `EnabledRefRW` 두 개로 통일.

**4. `EnabledRefRW` 를 쓰는 잡은 쿼리를 직접 만들어 넘김**

- `IJobEntity` 파라미터에 `EnabledRefRW<T>` 가 있을 때 기본 쿼리가 "켜진 것만" 인지 "있기만 하면" 인지를 **코드젠에 맡기지 않고** 명시.
  `WithAllRW<Active>` (켜진 것만) / `WithDisabledRW<Active>` (꺼진 것만, 재스폰) / `WithPresentRW<MaterialMeshInfo>` (상태 무관).
- 공식 문서 예제(`EnableableComponentExample.cs`)만으로는 기본 쿼리 필터링이 확정되지 않아서 택한 방어적 선택.

**5. 데미지 버스 — 스트림마다 적용 잡 하나씩 직렬 체인**

- 처음 설계: 등록된 스트림들을 `NativeArray<NativeStream>` 으로 잡 하나에 넘기기.
  → **컨테이너 안의 컨테이너는 잡 안전 검사에서 거부된다**는 걸 떠올리고 작성 중에 폐기.
- 그 전 초안은 적용 잡을 예약한 직후 `Complete()` 를 불러 사실상 메인 스레드 실행이었다 — 잡으로 만든 의미가 없어 폐기.
- 최종: 스트림마다 `ApplyDamageJob{Reader}` 를 `Schedule(chain)` 으로 직렬 연결, 해제(`stream.Dispose(handle)`)도 체인 뒤에 예약. 메인 스레드 대기 0.
- 버스 소유·해제 책임은 `DamageApplySystem` 한 곳 (Unity 의 ECB 시스템 싱글턴과 같은 패턴).

**6. 발사는 메인 스레드**

- 초당 2 회, 최근접 탐색도 발사 프레임에만 적 1,000 을 훑음. 잡 스케줄 비용이 더 크다고 판단.

**7. 재스폰 = 죽은 적 전부 즉시 링으로** (사용자 결정: 주기적 링 스폰)

- 풀 크기 = 목표 동시 적 수(1,000) 이므로 꺼진 적을 전부 살리면 수가 유지된다. **새 수치(보충 속도)가 필요 없는** 가장 단순한 형태.

**삼각형 2,760 의 해석**: 쿼드당 2 삼각형 × 2 배 제출(ISSUE-005) = 약 690 개만 실제로 그려지고 있다.
카메라 size 15 인데 적은 반경 12~40 에 흩어져 있어 나머지는 **프러스텀 컬링**으로 빠진 것. 정상이다.
**즉 이 수치는 "적 1000 마리를 다 그린 비용"이 아니다.** M2 벤치에서는 전부 화면에 넣어야 비교가 성립한다.

### 왜 이렇게 했나

**1. 분리(separation) 를 넣지 않음**

- **선택**: 순수 추격만. 적들이 플레이어 위에 겹쳐 쌓이는 걸 허용
- **선택 이유**: 이웃을 밀어내려면 주변 적을 찾아야 하고, 그러려면 공간 해시가 필요하다(기획서 8.3).
  공간 해시는 **M2 의 핵심 작업**이라 여기서 끌어오면 M1 덩어리가 통째로 커진다.
- **부수 효과**: 분리가 없으니 각 적이 자기 `LocalTransform` 만 건드리고 서로를 읽지 않는다.
  덕분에 `ScheduleParallel` 이 **무조건 안전**하다. 분리를 넣는 순간 이 단순함이 깨진다 — M2 과제.

**2. 적 스탯을 Blob 이 아니라 컴포넌트에 직접**

- **선택**: `EnemyMovement { Speed }` 로 엔티티마다 값을 들게 함
- **대안**: 기획서 8.4 대로 `EnemyTypeId(byte)` + Blob 스탯 테이블
- **선택 이유**: Blob 은 **타입이 여러 개일 때** 청크 파편화를 막는 구조다. M1 은 적이 1 종뿐이라
  구조만 복잡해진다. 적 6 종이 들어오는 M4 에서 전환한다.
  **단일 아키타입 원칙 자체는 지금도 지켜지고 있다** — 적은 모두 같은 컴포넌트 구성이다.

**3. 원본을 씬 오브젝트가 아니라 프리팹 에셋으로**

- **선택 이유**: Baker 가 **프리팹 에셋**을 변환하면 그 엔티티에 `Prefab` 컴포넌트가 붙어
  모든 쿼리에서 자동 제외된다. 씬 안의 오브젝트를 원본으로 쓰면
  **그 원본 자체가 살아있는 적이 되어 같이 플레이어를 쫓아온다.**
- M0 벤치마크는 씬 오브젝트를 원본으로 썼는데, 거기서는 렌더만 하므로 무해했다. 적은 다르다.

**4. 링 스폰에서 `sqrt` 로 반경 분포 보정**

- 반경을 균등 난수로 뽑으면 중심 쪽에 몰린다. 넓이는 반경의 제곱에 비례하기 때문이다.
  `sqrt(random)` 을 씌워야 링 전체에 고르게 퍼진다.
- 시드를 고정했다. 매 실행 같은 배치가 나와야 **성능 before/after 비교가 성립**한다.

**5. 오버슛 방지**

- 이번 프레임 이동량이 남은 거리보다 크면 플레이어를 지나쳤다가 다음 프레임에 되돌아오며 떨린다.
  `min(speed * dt, distance)` 로 잘라냈다.

**6. Unity CLI 도입 (작업 도중 결정)**

- 사용자가 `Unity-Technologies/skills` 레포를 제안. 확인해보니 **`com.unity.pipeline` 이 이미 프로젝트에
  들어 있었고 `unity` CLI 도 이미 설치돼 있었다.** 인프라가 전부 있는 상태였다.
- **가장 큰 이득은 에디터 락 해소**. 그동안 코드 수정마다 "에디터 닫아주세요 → 검증 → 다시 열기"
  왕복이 있었는데, `unity command recompile` 로 **켜둔 채 재컴파일**이 된다.
- 30 여 개 스킬 중 `unity-cli` / `unity-pipeline` 만 설치. 타일맵은 우리 지형 구조(자체 `NativeArray`
  그리드)와 안 맞고, 물리는 안 쓰기로 했고, IAP·광고·멀티플레이어는 무관하다.
  **스킬 설명이 컨텍스트에 올라가므로 안 쓰는 걸 깔면 소음만 된다.**
- `unity-check.sh`(배치모드 경로)는 **지우지 않았다.** 컴파일 에러가 나면 에디터가 Safe Mode 로 부팅되고
  그러면 Pipeline 이 로드되지 않아 CLI 연결 자체가 안 된다. 그때는 배치모드가 유일한 수단이다.

**7. asmdef 이름 단축 (사용자 요청)**

  - 네임스페이스: 폴더 경로를 따라야 IDE 가 위치 불일치를 검증해준다
  - `rootNamespace` 로 연결한다

**검증**: WASD 이동 정상, 대각선 속도 = 직선 속도 (사용자 확인)

### 왜 이렇게 했나

**1. 플레이어를 MonoBehaviour 가 아니라 엔티티로**

- **선택**: 플레이어도 엔티티. 매니지드 코드는 입력 읽는 시스템 하나뿐
- **대안**: (a) 하이브리드 — GameObject + SpriteRenderer + Animator (b) M1 은 하이브리드로 가고 M3 에 전환
- **논의 과정**: "외부 2D 스프라이트 에셋을 쓸 거면 하이브리드가 편하지 않나"라는 질문이 나왔고,
  이건 타당한 지적이었다. 하지만 **적 1만 마리도 스프라이트**라는 점이 계산에서 빠져 있었다.
  `SpriteRenderer` 는 Entities Graphics 에서 못 쓰므로 적·투사체·젬은 어차피
  **아틀라스 + 쿼드 + 머티리얼 프로퍼티 UV 오프셋** 경로를 만들어야 한다(기획서 8.5).
  그 경로를 만들고 나면 플레이어는 같은 경로를 공짜로 쓴다.
  즉 "스프라이트를 쓴다"는 사실 자체는 하이브리드의 근거가 되지 못한다.
- **선택 이유 (결정적)**: **지형 시스템**. 기획서상 플레이어는 연소 타일에서 피해를 받고,
  빙판에서 이동속도가 바뀌고, 균열에서 속도가 변한다. 이게 전부 타일 그리드 잡 안에서 일어나는데
  플레이어만 GameObject 면 **이 판정을 플레이어용으로 한 번 더 따로 짜야 한다.**
  부차적으로, 하이브리드는 BRG 엔티티와 SpriteRenderer 라는 **렌더 경로 2개**가 생겨
  둘 사이의 앞뒤 정렬(렌더 큐 vs Sorting Layer)이 까다로워진다.
- **포기한 것**: `Animator` 와 애니메이션 편집 워크플로우. 플레이어 애니메이션을 UV 프레임 인덱스로
  직접 계산해야 한다. 뱀서라이크 플레이어는 보통 idle/walk 몇 프레임 + 좌우 반전 + 피격 플래시라
  감당 가능하다고 판단.
- **탈출구**: Entities 에 `Unity.Entities.Hybrid.HybridComponents` (Companion GameObject) 가 있다.
  애니메이션이 정말 복잡해지면 **플레이어 1개에만** GameObject 를 붙여 `Animator` 를 쓸 수 있다.
  1만 개에 쓰면 망하지만 1개는 비용이 무의미하다. **되돌리기 어려운 결정이 아니다.**

**2. 입력만 SystemBase, 나머지는 전부 ISystem + Burst**

- **선택 이유**: `InputActionAsset` / `InputAction` 은 매니지드 클래스라 Burst ISystem 에서 다룰 수 없다.
  매니지드 경계를 **이 시스템 하나로 격리**하고, 읽은 값을 싱글턴 컴포넌트에 써두면
  이후 모든 게임플레이 시스템은 Burst 로 컴파일된 채 그 값을 읽는다.
  플레이어를 엔티티로 둔 이유(동기화 경계 최소화)가 실제 구조로 구현된 지점.

**3. 새 Input Actions 를 만들지 않고 기존 `Player/Move` 재사용**

- 프로젝트에 `InputSystem_Actions.inputactions` 가 이미 전역 액션으로 설정돼 있었고
  `Player/Move` 가 Vector2 + WASD 로 구성돼 있어 그대로 썼다. API 존재 여부(`InputSystem.actions`,
  `InputActionAsset.FindAction`)는 패키지 소스에서 직접 확인한 뒤 사용.

**4. 대각선 정규화를 입력 단계에서**

- WASD 는 (1,1) 이 들어와 길이가 √2 가 된다. 정규화하지 않으면 대각선이 41% 빠르다.
- **길이가 1 을 넘을 때만** 정규화한다. 게임패드 아날로그 스틱은 살짝 기울인 상태의 길이가
  1 미만인데, 무조건 정규화하면 미세 조작이 전부 최대 속도가 되어버린다.

**5. 플레이어를 싱글턴이 아니라 Query 로 순회**

- 플레이어는 1 개지만 `SystemAPI.Query` 로 돈다. 싱글턴으로 강제하면 나중에 구조를 바꿔야 하고,
  1 개짜리 순회는 비용이 사실상 0 이다.

**6. 카메라는 MonoBehaviour 유지**

- 카메라는 Unity 매니지드 오브젝트라 어차피 GameObject 다. 중요한 건 이게 **ECS 를 읽기만 하는
  단방향**이라는 점 — 양방향 동기화 버그가 생길 여지가 없어 "플레이어를 엔티티로" 결정과 충돌하지 않는다.
- `LateUpdate` 에서 갱신한다. 시뮬레이션이 플레이어를 움직인 뒤 따라가야 한 프레임 밀리지 않는다.
- 추적 보간은 `1 - exp(-k * dt)` 를 쓴다. `Lerp(a, b, k * dt)` 는 프레임률에 따라 추적 속도가 달라진다.

**1. 벤치 구성: SubScene 프로토타입 1개 + 런타임 대량 복제**

- **선택**: SubScene 에 렌더 가능한 GameObject 하나만 베이킹하고, 시스템이 `Instantiate` 로 1만 개 생성
- **대안**: SubScene 에 1만 개 GameObject 를 직접 배치해 베이킹
- **선택 이유**: 베이킹 검증과 "원본 1개 → 대량 복제"라는 **실제 게임의 풀링 경로를 동시에 검증**한다.
  Entities Graphics 가 렌더 컴포넌트(MaterialMeshInfo, RenderBounds 등)를 베이킹 때 붙여주므로
  렌더 컴포넌트 구성을 손으로 만들 필요도 없어진다.
- **포기한 것**: 대량 베이킹 자체의 비용은 측정하지 못함. 지금은 관심사가 아니라 감수.

**2. 격자 배치 (무작위 아님)**

- **선택 이유**: 무작위 배치는 겹침 정도가 실행마다 달라져 실제 그려지는 픽셀 수가 흔들린다.
  격자는 결정적이라 **before/after 비교가 성립**한다. 최적화 작업의 전제 조건이다.

**3. 카메라 직교 size 65 (영역 120u 전체가 화면에)**

- **선택 이유**: 일부만 보이면 프러스텀 컬링이 개입해 수치가 실제보다 좋게 나온다.
  벤치마크는 **가장 불리한 조건**에서 재야 의미가 있다.

**4. 씬 자동 생성을 도입했다가 철회**

- **처음 선택**: 에디터 스크립트로 씬까지 코드로 구성 (`BenchmarkSceneBuilder`)
- **철회 이유**: 사용자가 씬 작업은 직접 하는 쪽을 택함. 에디터에서 보면서 조정하는 게 빠르고,
  스크립트는 수정할 때마다 재실행해야 해서 오히려 느리다.
- **결과**: `BenchmarkSceneBuilder` 삭제 → 머티리얼 생성만 남긴 `BenchmarkAssetBuilder` 로 축소.
  CLAUDE.md 3.3 을 **"씬은 사용자, 에셋은 Claude"** 로 개정.
- 다만 철회 전에 배운 것이 있다: 배치모드는 "이름 없는 미저장 씬"으로 시작해서
  additive 씬 생성이 거부된다. 메인 씬을 Single 로 먼저 열어야 한다.

### 배운 것 / 다음에 다르게 할 것

- **DOTS 렌더 성능을 구형 렌더러 카운터로 판단하면 안 된다.** `instancedBatchedDrawCalls` 가 0 이라

### 왜 이렇게 했나

**1. 차별화 축을 "지형 시뮬레이션"에 집중**

- **선택**: 지형을 상태를 가진 타일 그리드 시뮬레이션으로 만들고, 무기가 지형을 조작 → 지형이 다시 무기를 증폭시키는 구조
- **대안**: (a) 무기 진화만 파기 (원작 답습) (b) 지형을 단순 시각 연출로만 처리
- **선택 이유**: 무기 진화와 지형을 각각 독립적으로 넣으면 둘 다 평범해진다. 둘을 엮어서 **킬러 콤보를 전부 "무기 2개 + 지형"의 3항 조합**으로 설계하면, 무기만 모아선 강해질 수 없는 고유한 빌드 설계 재미가 생긴다. 동시에 수십만 타일 시뮬레이션은 **DOTS를 쓰는 기술적 명분 그 자체**라 포트폴리오 관점에서도 1만 유닛보다 설명거리가 많다.
- **포기한 것**: 구현 범위가 크게 늘어남 (타일 그리드 + 상태 전파 Job + 지형 렌더링이 통째로 추가). 지형이 재미없으면 기획의 절반이 무너지는 리스크를 안음 → M3에서 최소 3개 무기로 조기 검증하는 걸로 완화.

**2. 목표 밀도 1만 + M2를 게이트로 설정**

- **선택**: M2(공간 해시·풀링·인스턴싱 렌더로 적 1만 @60fps)를 통과하기 전엔 M3 이후 콘텐츠를 만들지 않는다
- **선택 이유**: 성능 뼈대(풀링, 공간 해시, 단일 아키타입)는 **나중에 끼워넣는 비용이 압도적으로 크다.** 콘텐츠를 먼저 쌓은 뒤 성능이 안 나오면 전부 다시 써야 한다.
- **포기한 것**: 초반에 눈에 보이는 결과물이 적어 동기 부여가 떨어짐 → M1에서 적 1,000 규모의 플레이 가능한 루프를 먼저 만들어 완화.
