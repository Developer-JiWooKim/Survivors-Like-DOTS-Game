## 2026-09-18 (4) — [M3] 맵 크기 확정 + 지형 피해

**커밋** (미커밋) | **관련 이슈** 없음

지형이 **게임플레이가 되는** 지점. 여기까지 와야 지형 콤보가 실제로 적을 죽인다.

### 결정 — 맵 128×128 (기획서 4.1 변경)

덩어리 3 의 육안 검증에서 **맵 크기가 실제로 막는 문제**가 드러났다.

| | 값 | 문제 |
|---|---|---|
| 맵 (검증 당시) | 32×32 = 1,024 칸 | |
| 스폰 링 | 플레이어 기준 32~36 u | **맵 전체보다 크다** → 적이 전부 지형 바깥에서 스폰 |
| 리사이클 | 45 u | 같은 이유 |
| 감전 상한 | 2,000 칸 | 맵 전체(1,024)보다 커서 **아무 일도 하지 않음** |

지형 피해를 넣으면 **적 대부분이 지형 위에 없어** 상호작용이 거의 발생하지 않는다.
기획서의 512×512 로 돌아가면 이 문제는 사라지지만 **벽까지 걸어가는 데만 수 분이 걸려 경계를 테스트할 수 없다.**

**사용자 결정: 128×128.** 시야(~30×17 u)의 약 4 배 — 스폰 링·리사이클을 그대로 쓰면서
경계와 지형 상호작용을 실제로 확인할 수 있는 최소 크기다. 그리드는 64 KB.

**남은 구멍**: 맵 가장자리에 서면 스폰 링의 일부가 여전히 맵 밖이다. 적 벽 충돌이 들어오면 완화된다.

### 한 일

| 파일 | 내용 |
|---|---|
| `Runtime/Terrain/TerrainDamage.cs` (신규) | 타일 → 초당 피해 **순수 함수** |
| `Runtime/Terrain/TerrainDamageSystem.cs` (신규) | 적·플레이어가 선 칸을 읽어 데미지 버스로 (병렬) |
| `Runtime/Terrain/TerrainTickSettings.cs` · `TerrainAuthoring.cs` | 연소 12/s · 감전 40/s · 기름 ×2, 맵 기본값 512 → 128 |
| `Tests/Terrain/TerrainDamageTests.cs` (신규) | 테스트 7 개 |

### 왜 이렇게 했나

**1) 지형 틱(10Hz)이 아니라 매 프레임 `초당피해 × dt`**

기획서가 정한 건 "**초당** 피해" 다. 프레임마다 dt 를 곱하면 프레임률과 무관하게 총량이 같고,
"이번 프레임에 틱이 돌았나" 를 시스템 간에 공유할 필요도 없다.
타일 조회는 배열 인덱싱 하나라 적 1 만에도 병렬 잡으로 싸다.

**2) Health 를 직접 깎지 않고 데미지 버스 (기획서 8.3)**

같은 적이 같은 프레임에 투사체에도 맞으면 두 워커가 같은 Health 에 쓰는 레이스가 된다.
**발생원이 늘어도 적용은 한 곳**이라는 규칙을 지킨다 — `DamageEventBus` 주석이 예고한
"지형" 발생원이 실제로 들어온 셈이다.

**3) 플레이어에게 무적 프레임을 주지 않는다**

접촉 피해는 0.5 초 무적이 붙지만(기획서 3 장), 지형 피해에 같은 걸 적용하면
**불 위에 서 있어도 절반이 공짜**가 된다. 기획서 4.4 의 "화면 전체를 불바다로 만들면 자기 무덤" 이
성립하려면 지속 피해는 지속으로 들어가야 한다.

**4) 적과 플레이어를 같은 잡 타입으로**

규칙이 동일하기 때문이다 (기획서 4.4 — 불은 플레이어도 태운다). 쿼리만 둘로 나눠 같은 잡을 두 번 예약한다.
분기를 만들지 않으면 "적만 안 아프다" 같은 비대칭 버그가 생길 자리가 없다.

**5) 기름 배수는 연소에만, 감전에는 안 곱한다**

기획서 4.3 의 "기름은 피해 2 배" 는 연소 이야기다. 감전까지 곱하면 전격 피해가 지형에 따라 2 배가 되는
**기획서에 없는 규칙**이 생긴다. 테스트로 못 박았다 (`OilMultiplierAppliesOnlyToBurn`).

### 측정 준비 — T 키 (대규모 점화)

성능 측정을 하려면 **같은 최악 조건을 반복해서 만들 수단**이 필요하다.
F 로 한 칸 점화하고 확산을 기다리면 측정 시점마다 불의 규모가 달라져 비교가 불가능하다
(ISSUE-005 에서 A/B 조건이 달라 수치를 버렸던 것과 같은 함정 — CLAUDE.md 4 장).

**T = 반경 30 u 즉시 점화.** 이미 있던 `TerrainEffectKind.Ignite` 를 큰 반경으로 부르는 것뿐이라
새 코드 경로가 아니다. 게임플레이용이 아니라 측정 전용이다.

### 성능 측정 — 1 회차 (2026-09-18) : **A/B 비교로는 무효**

> 측정 환경: 에디터 플레이 모드, 사용자 측정, 빌드 아님. Profiler·Frame Debugger 끔, SSAO 끔.
> 맵 128×128, 창 50×50. **벤치마크 고정 목표를 쓰지 않고** 스폰 디렉터가 늘리는 대로 두다가
> 적 개체가 20,000 이 된 시점에 측정.

| 조건 | FPS | Main | Tris |
|---|---|---|---|
| A 지형 없음 (`Terrain` 비활성화) | 190 | 5.46 ms | 22,681 |
| B 지형 있음, 불 없음 | 180 | 5.13 ms | **19,539** |
| C 지형 + 불바다 (T 키) | 171 | 6.4 ms | 25,209 |

**왜 무효인가 — Tris 가 조건 불일치를 드러낸다**

지형을 켜면 창(50×50)의 쿼드 2,500 개 = **약 5,000 Tris 가 더해져야** 한다.
그런데 B 가 A 보다 Tris 가 **3,142 적다.** 즉 B 는 A 보다 화면 안의 적이 **약 4,000 마리 적었다.**

같은 이야기를 Main 도 한다 — B(5.13)가 A(5.46)보다 **낮다.** 시스템을 추가했는데 메인 스레드가
줄어들 수는 없다. 개체 수가 달랐다는 것 외엔 설명이 안 된다.

C 도 B 보다 Tris 가 5,670 많다. **불은 색만 바꿀 뿐 지오메트리를 늘리지 않으므로** C 역시 적이 더 많았다.
그러면 C 의 FPS 하락이 불 때문인지 적 때문인지 가릴 수 없다.

**원인**: 스폰 디렉터가 시간에 따라 목표를 계속 늘리는 중이라 세 측정 시점의 살아있는 적 수가 달랐다.
ISSUE-005 에서 겪은 것과 **같은 종류의 함정**이다 — 그때는 Profiler 켜짐 여부, 이번엔 개체 수.

**그래도 건진 것 (유효한 절대 수치)**

### C (불바다) 재측정 — 유효

> 같은 세션·같은 설정. **정지하지 않고** T 를 누른 2 초 뒤 실행 중에 읽음.

| | A 지형 없음 | B 지형, 불 없음 | **C 불바다** |
|---|---|---|---|
| FPS | 256.0 (3.91 ms) | 251.1 (3.98 ms) | **225.5 (4.43 ms)** |
| Main | 3.65 ms | 3.84 ms | **4.20 ms** |
| Draw | 13 | 15 | 14 |
| Tris | 20,401 | 23,657 | **23,675** |
| Enemy | 10000/10000 | 10000/10000 | **9997/10000** |

**조건 검산 통과**: Tris 가 B 와 사실상 동일(23,675 vs 23,657) — 불은 색만 바꾸므로 지오메트리가 같아야 맞다.
`Enemy 9997/10000` 은 **적이 불에 타 죽고 있다**는 증거다 (스폰 디렉터가 곧바로 채운다).

| 구간 | 프레임 | 메인 스레드 |
|---|---|---|
| A → B (지형 상시 비용) | +0.07 ms | +0.19 ms |
| B → C (불바다 추가 비용) | **+0.45 ms** | **+0.36 ms** |
| **A → C (지형 전체 최악)** | **+0.52 ms** (13%) | **+0.55 ms** (15%) |

**해석**

- **60fps 예산 16.6 ms 대비 3.1%.** 최악 조건에서도 225 FPS 로, M2 게이트(60fps)의 3.75 배다.
- B → C 의 +0.45 ms 는 **확산 잡만의 비용이 아니다.** 불이 적을 죽이므로 사망 처리 · 젬 스폰 ·
  재스폰이 함께 돈다. 즉 이 수치는 "지형 시뮬레이션" 이 아니라 **"지형이 게임플레이를 굴릴 때의
  연쇄 비용 전체"** 이고, 실제 플레이에 가까운 값이다.
- 확산 잡 자체를 따로 떼어 재려면 피해를 끈 채로 측정해야 하는데, **그럴 이유가 없다** —
  전체가 0.52 ms 라 어느 쪽이 얼마인지 알아도 할 일이 달라지지 않는다.
  (기획서 8.6 프레임 예산에서 지형에 배정한 몫 대비 한참 아래다.)

### 예측이 빗나간 곳 — 렌더 비용은 창이 아니라 **화면 크기**에 묶인다

"지형을 켜면 창 크기만큼 Tris 가 는다" 고 예상하고 +5,000 을 불렀는데 실제는 **+3,256** 이었다.

| | 값 |
|---|---|
| 타일 풀 (Ents 증가분) | 3,024 개 |
| 실제로 그려진 타일 (Tris ÷ 2) | **1,628 개** |
| 카메라 시야 (ortho 15, 16:9) | 약 53 × 30 = 1,590 타일 |

**Entities Graphics 의 프러스텀 컬링이 창 밖 쿼드를 걸러낸다.** 그려진 수가 시야 크기와 거의 정확히 맞는다.

- 창을 넉넉히 잡아도 **그리는 양은 안 늘어난다** — 가장자리가 비지 않게 여유를 두는 비용이 생각보다 싸다.
- 다만 **컬링 판정 자체는 풀 전량(3,024)에 대해 돈다.** 그게 위 0.19 ms 안에 포함된 값이다.
- 덩어리 1 에서 "텍스처 1 장 vs 엔티티 풀" 을 고를 때 걱정한 "쿼드 갱신 비용" 은
  실측으로 **0.19 ms** 였다. 텍스처 방식의 이점(1 MB 업로드 회피)과 맞바꿀 만한 값이 아니었다 —
  **즉 그때의 선택은 결과적으로 옳았고, 근거도 이제 추측이 아니라 수치다.**

  나머지는 전부 같은가" 를 항목으로 적고 시작하자.**

- **오버레이를 일시정지한 채 찍으면 수치가 깨진다** (2 회차 C). `Main 0.16 ms` 인데 프레임이 64 ms 인

- **프러스텀 컬링을 계산에 넣지 않았다.** "창 크기 = 렌더 비용" 으로 예측했다가 빗나갔고,

### 왜 이렇게 했나

**1) 감전은 메인 스레드 BFS (사용자 결정 2026-09-18)**

**대안**: 연소처럼 틱마다 한 칸씩 번지게 하기 / 맵 생성 시 물 덩어리를 미리 라벨링해 두기.

**선택 이유**:
- 틱마다 한 칸씩은 병렬 잡으로 공짜지만 **기획서 4.3 의 "같은 틱" 을 어긴다.** 감전 지속이 0.5 초 = 5 틱이라
  큰 웅덩이는 끝까지 번지기 전에 앞쪽이 꺼진다. 전격의 "한 방에 터진다" 는 타격감이 사라진다.
- 미리 라벨링은 감전 순간이 가장 싸지만, **지형이 변하는 게 이 게임의 핵심**이다 —
  물이 얼고 녹고, 기름이 덮이고, 지진파가 땅을 부순다. 그때마다 라벨을 갱신해야 하고 그 갱신이 결국 flood fill 이다.
  복잡도만 늘고 비용은 안 줄 가능성이 높다.

**포기한 것**: 비용이 물 덩어리 크기에 비례한다. **방문 칸 수 상한(기본 2,000)** 으로 막았다.

상한이 만든 부수 효과가 있다 — 상한을 넘는 호수는 일부만 감전된다. 이건 결함이 아니라
**밸런스 안전장치**다. 맵 절반이 물인 구역에서 전격 한 발로 화면을 청소하는 것을 막는다
(기획서 4.4 가 비행 적으로 막으려는 것과 같은 종류의 일). 성능 상한과 밸런스 상한이 같은 숫자인 셈이다.

**2) 무기가 그리드를 직접 고치지 않고 효과 큐를 거친다**

화염구·전격 사슬은 아직 없지만, 경로를 지금 정해 뒀다.

- **투사체 충돌은 병렬 잡에서 일어난다.** 거기서 그리드를 직접 고치면 여러 스레드가 같은 칸에 쓰는 레이스가 된다.
  감전은 한 요청이 수천 칸을 건드리므로 특히 위험하다. (`DamageEventBus` 가 피해를 모았다가 한 곳에서 적용하는 것과 같은 이유.)
- flood fill 은 메인 스레드라 잡 안에서 부를 수 없다.

`NativeQueue` 를 고른 건 `ParallelWriter` 가 있어서다 — 지금은 디버그 키가 메인 스레드에서 넣지만,
무기가 들어오면 충돌 잡에서 병렬로 넣는다. **디버그 키가 이미 무기가 쓸 경로를 그대로 쓰고 있다.**

**3) Timer 가 하나뿐인 제약을 어떻게 넘겼나**

`TileData` 4 byte 예산(기획서 4.1)에 타이머는 1 byte 뿐인데, 감전·동결·오염이 각각 시간을 가진다.

지금은 충돌하지 않는다 — **감전은 물에, 동결은 그 물을 빙판으로 바꿔** 걸리므로 두 상태가
같은 타일에 동시에 존재할 수 없다 (`Freeze` 가 감전을 지운다). 연소는 `Fuel` 이 시계라 Timer 를 안 쓴다.

**오염(독 안개, M4)이 들어오면 감전과 겹칠 수 있다.** 그때 Timer 를 어떻게 나눌지 정해야 한다 —
클래스 주석에 남겨 뒀다. 미리 만들지 않고 충돌이 실제로 생길 때 결정한다.

**4) 얼음은 전기를 통하지 않는다**

기획서에 명시가 없다. `IsWaterLike` 에서 물·물 위 기름만 포함하고 빙판은 뺐다.
**"얼려서 물길을 끊는다" 는 플레이를 살리기 위해서**다 — 서리 파동과 전격 사슬이 서로를 방해할 수 있어야
빌드 선택에 의미가 생긴다. 기획서 5.4 의 "절대영도 + 폭풍" 콤보와는 층이 다르다(그쪽은 빙결된 **적**의 연쇄).

**5) 타이머 처리는 확산 **뒤**에**

### 배운 것 / 다음에 다르게 할 것
- **같은 실수를 두 덩어리 연속으로 했다** — `in TerrainGrid` 로 받아 `NativeArray` 에 쓰려다 컴파일 실패.

  (`NativeArray` 는 참조라 값 전달해도 실제 데이터는 복사되지 않는다). 다음부터 그리드·해시처럼
  컨테이너를 든 싱글턴은 **쓰기 경로에서 값으로 받는다**.
- **Burst 가 델리게이트를 못 쓴다는 걸 다시 확인했다.** 반경 루프 3 개가 거의 같아 콜백으로 묶으려 했다가
  되돌렸다. DOTS 에서는 "중복을 줄이는 리팩터링" 이 컴파일 자체를 막는 경우가 있다 — 묶기 전에 Burst 를 먼저 생각하자.
- **상한이 밸런스 장치가 되는 걸 이번에 처음 의식했다.** 성능 때문에 넣은 숫자가 게임 규칙이 됐다.
  이런 건 "성능 상수" 가 아니라 **기획 수치로 문서에 올려야** 나중에 밸런싱할 때 찾을 수 있다.
- 디버그 키를 무기가 쓸 경로(효과 큐)로 연결해 둔 게 값을 할 것 같다. 화염구가 들어올 때
  **큐에 넣는 한 줄만 추가**하면 되고, 디버그 키로 이미 검증된 경로를 탄다.
- **확인 항목을 적을 때 그 상황이 현재 설정에서 발생 가능한지 따지지 않았다** (6 번).
  상한 2,000 이 맵 전체 칸 수 1,024 보다 크다는 건 값 두 개만 비교하면 나오는 사실인데
  그냥 "큰 호수에서 확인하라" 고 넘겼다. **육안 확인을 요청할 때는 재현 조건이 성립하는지 먼저 계산하자.**

### 왜 이렇게 했나

**1) 규칙을 잡에서 떼어내 순수 함수로 (`BurnRules`)**

**선택 이유**: 확산 버그는 "가끔 한 칸 더 번진다 / 소화가 한 틱 늦다" 형태다. 적 1 만 마리가 뛰는 화면에서
눈으로 잡을 수 있는 종류가 아니고, 틀리면 지형 콤보(이 게임의 차별화 축) 체감이 통째로 어긋난다.
CLAUDE.md 5 장이 "지형 연소 확산 규칙" 을 테스트 대상으로 지목한 이유이기도 하다.

**포기한 것**: 잡 안에 규칙을 인라인하면 함수 호출이 없어 이론상 더 빠르다. Burst 가 static 함수를
인라인해 줄 것으로 보지만 **측정하지 않았으므로 빠르다고 주장하지 않는다.** 규칙이 바뀌는 단계라
검증 가능성이 우선이고, 성능 문제가 관측되면 그때 인라인한다.

**2) 더블 버퍼링 (기획서 8.3)**

제자리에서 고치면 먼저 처리된 칸의 **이번 틱 결과**를 옆 칸이 읽어서, 불이 한 틱에 여러 칸을 건너뛰고
그 거리가 **잡의 실행 순서에 따라 달라진다**. 읽기/쓰기를 갈라 모든 칸이 같은 스냅샷을 보게 했다.
`Spread_MovesAtMostOneCellPerTick` 테스트가 정확히 이걸 지킨다 (확률 1.0 에서 맨해튼 거리 = 틱 수).

스왑은 잡을 띄운 **직후** 메인 스레드에서 한다. 잡이 배열 구조체를 값으로 복사해 가므로 안전하다.

**3) 난수를 타일당 한 번만 굴린다**

기획서 4.3 은 "불타는 타일이 주변으로 확률 전파" 라 이웃마다 굴리는 게 직역이다. 그러려면
"몇 번째 이웃" 까지 해시에 넣어야 하고, 같은 타일이 한 틱에 여러 난수를 쓰게 되어 재현이 번거로워진다.
받는 쪽에서 **한 번만** 굴리고 확률을 `1 - (1-p)^n` 으로 쓰면 분포는 같고 결정성은 자명해진다.

여기서 함정이 하나 있었다 — `p` 가 1 을 넘으면 `1-(1-p)^n` 이 **진동해서 이웃이 2 개일 때 확률이 되레 떨어진다.**
기름은 ×3 이라 착화 확률 0.34 만 넘어도 발생한다. `IgniteChancePerNeighbor` 에서 saturate 하고
`IgniteChance_ChancePerNeighborIsClampedToOne` 로 고정했다.

**4) 해시 설계 — 인덱스와 틱을 각각 섞은 뒤 다시 해시**

처음엔 `hash(index) ^ tick` 정도를 생각했는데, 그러면 `(index+1, tick)` 과 `(index, tick+1)` 이 같은 값이 되어
**확산이 대각선 줄무늬로 보인다.** 두 값을 각각 해시한 뒤 합쳐서 상관을 끊었다.
`Random01_DoesNotCorrelateIndexWithTick` 가 이 실수를 막는다. 눈으로 보기 전에 테스트가 먼저 잡는 종류의 버그다.

**5) 밀린 틱을 몰아서 처리하지 않는다**

프레임이 길어졌을 때 밀린 틱을 다 돌리면 렉이 걸린 순간 불이 순간이동한 것처럼 번진다.
밀린 만큼은 버리고 다음 프레임에 한 번만 돈다. 시뮬레이션 정확도보다 **눈에 보이는 일관성**을 택했다.

**6) 확산은 `GameplaySystemGroup` 안, 렌더는 밖**

레벨업으로 멈춘 동안 불이 계속 번지면 "멈춰 있는데 상황이 나빠지는" 상태가 된다.
렌더만 그룹 밖이라 정지 중에도 화면은 유지된다 (덩어리 1 에서 정한 배치가 그대로 맞아떨어졌다).

**7) 디버그 점화를 Input Actions 에셋이 아니라 `Keyboard.current` 로**

액션 에셋 편집은 사용자 몫인데(CLAUDE.md 3.4), 화염구·기름통이 들어오면 지워질 디버그 키 때문에
그 절차를 요구할 이유가 없다. `#if UNITY_EDITOR || DEVELOPMENT_BUILD` 로 릴리스에서 빠진다.

### ISSUE-012 — 물 위 기름 (발견 → 결정 → 해결)

**증상**: 물을 **완전히 덮도록** 기름을 바르고 태우면 물 타일이 통째로 사라진다 (다 탄 뒤 흙).
부분적으로 덮었을 때는 물 쪽으로 번지지 않아 정상으로 보였다.

**원인**: 기름을 칠할 때 타일을 통째로 덮어써서(바위만 예외) 물이라는 정보가 그 시점에 사라지고,
연소가 끝나면 기획서 4.3 대로 흙이 된다. 근본은 **`TileData` 4 byte 안에 "원래 무엇이었나" 를
담을 자리가 없다**는 것.

**기획서 미명시 지점**이라 고치기 전에 선택지를 정리해 사용자 판단을 받았다 →
**결정: 기름이 물 위에 뜨고, 다 타면 물로 돌아간다.**

**해결 방식**: `TileData` 에 필드를 더하는 대신 **`TileType.OilOnWater` 라는 종류를 하나 추가**했다.
Type 값 하나를 더 쓰는 것으로 같은 정보를 표현하므로 **메모리 증가가 0** 이고 4 byte 예산이 유지된다.
확산 확률 3 배는 두 기름 모두에 붙고, 앞으로 들어올 감전 flood fill · 동결은 물 위 기름도 물로 본다
(`TileTypes.IsWaterLike`) — 전격·냉기 콤보가 그대로 성립해야 하기 때문.

자세한 대안 비교와 재발 방지는 [ISSUE-012](IssueLog.md#issue-012).

**재검증 (사용자, 2026-09-18)**: 물 위 기름을 태운 뒤 물이 정상 복귀하는 것 확인. 커밋 `0b45cec`.

### 테스트 24 개가 고정한 것
| 분류 | 검증 내용 |
|---|---|
| 난수 | 결정성 / 0≤x<1 / 인덱스-틱 무상관 / 균등 분포 |
| 가연 조건 | 연료 있는 풀·기름만. 물·바위·흙은 확률 1.0 에서도 안 붙음 |
| 확률 | 이웃 0 이면 0 / 기름 = 풀 ×3 / 이웃 수에 따라 증가 / 1 로 clamp |
| 한 칸 전진 | 틱당 연료 1 감소 / 연료 0 → 흙 + 소화 / **연료 = 지속 틱 수** / 붙은 틱엔 연료 안 깎임 / 다른 상태 비트 보존 |
| 그리드 확산 | **틱당 최대 한 칸** / 대각선 안 감 / 맵 경계에서 안 감싸 돎 / **물이 방화선** / 다 타면 흙 되고 멈춤 / 재실행 결과 동일 / 기름이 풀보다 빠름 |

### 성능 측정
아직 없음. 다음 측정에서 **적 10,000 + 맵 전체 연소**를 M2 기준(에디터 150~203 FPS, 메인 6.2 ms)과 비교한다.
관심사는 확산 잡이 아니라 **10Hz 마다 그리드 전체를 훑는 것이 메인 스레드에 얼마나 얹히는가**다.

### 배운 것 / 다음에 다르게 할 것
- **확률을 합치는 공식에 함정이 있었다.** `1-(1-p)^n` 은 `p>1` 에서 진동한다. 기름 ×3 배수와 곱해지는
  순간 실제로 도달 가능한 구간이라, "확률에 배수를 곱한다" 는 기획서 문장을 그대로 코드로 옮기면 버그가 된다.
  **배수가 붙는 확률은 항상 clamp 지점을 먼저 생각하자.**
- **테스트가 눈보다 먼저 잡는 버그가 있고, 눈이 테스트보다 먼저 잡는 버그가 있다.** 인덱스-틱 상관은
  테스트로 잡았지만, 해시 품질이 만드는 격자 패턴은 결국 봐야 안다. 확인 항목에 6 번을 넣은 이유다.
- 덩어리 1 에서 "렌더를 게임플레이 그룹 밖에 둔다" 고 정한 게 이번 덩어리에서 그대로 값을 했다.
  **일시정지 경계를 미리 정해두면 나중 시스템이 어디 들어갈지 고민할 필요가 없다.**
- **테스트가 못 잡는 층이 있다는 걸 ISSUE-012 가 보여줬다.** 확산 규칙 테스트 24 개는 "기름이 탄다" 를
  정확히 검증했지만 **"기름 아래 무엇이 있었나" 는 묻지 않았다.** 버그는 규칙이 아니라
  *규칙에 들어가기 전에 정보를 지운 곳*(칠하기)에 있었다. 순수 함수 테스트는 함수 안쪽만 지킨다.
  확인 항목을 단계로 적어 사용자에게 넘긴 절차가 그 바깥을 잡았다.
- **"덮어쓰기" 는 정보를 지우는 연산이다.** 바위만 예외 처리하고 물을 빠뜨린 게 원인이었다.
  되돌아와야 하는 상태를 덮어쓸 때는 "무엇을 잃는가" 를 먼저 묻자.
- **4 byte 예산이 오히려 더 나은 설계를 강요했다.** "원래 타입" 필드를 더하고 싶었지만 예산에 막혀
  타일 **종류**로 표현하게 됐고, 결과적으로 메모리 증가 0 에 색·확산·감전 분기까지 자연스럽게 붙었다.

## 2026-09-18 (1) — [M3] 타일 그리드 + 맵 생성 + 화면 부근 타일 렌더

**커밋** `bdf3fe0` | **관련 이슈** 없음

M3 진입. 기획서 11 장에 M3 전에 결정하라고 적어 둔 미결 2 건을 먼저 처리하고, 첫 덩어리로
**"지형이 화면에 보이는 것"** 까지 만들었다. 확산·상호작용은 다음 덩어리.

### 결정 1 — 맵 경계: 512×512 유한 맵 + 벽 (기획서 11 장 #1)

**대안**: 토러스 래핑(무한 스크롤) / 유한 맵 + 소프트 경계(밀어내기).

**선택 이유**:
- 토러스는 연소 확산·flood fill·타일 조회 **전부에 모듈로**가 들어간다. 확산 잡의 핫 루프에 나눗셈이 붙는다.
- 월드 좌표와 타일 좌표가 어긋나 렌더·카메라 쪽에도 래핑 처리가 번진다.
- M2 A/B 측정에서 **병목이 CPU 메인 스레드(≈6.2 ms)** 로 확인됐다. 지금 CPU 비용을 더할 이유가 없다.
- 512 u 는 카메라 시야(~30×17 u)의 17~30 배라 20 분 런에서 벽에 닿을 일이 드물다.

**포기한 것**: 맵 끝에 몰리면 플레이어가 구석에 갇혀 지형 콤보가 무의미해진다.
빈도가 낮다고 보고 감수했다. M4 플레이테스트에서 실제로 구석 플레이가 나오면 소프트 경계로 바꾼다.

**부수 효과 하나가 공짜로 따라왔다**: 경계 밖 조회를 `Rock` 으로 돌려주면(`TerrainGrid.TileAt`)
확산 잡이 **경계 분기를 아예 두지 않아도** 불이 맵 끝에서 자연히 멈춘다. 벽이라는 기획 결정이
곧 확산 알고리즘의 종료 조건이 된 셈이다.

### 결정 2 — 연소 확산 난수: (타일 인덱스 + 틱) 해시 (기획서 11 장 #2)

**대안**: 타일마다 `Random` 시드를 저장하고 매 틱 전진 / 난수 없이 결정적 규칙(연료·이웃 수만으로).

**선택 이유**:
- 난수를 **그 자리에서** 만들면 잡 실행 순서와 무관하게 같은 틱·같은 타일이 항상 같은 값을 갖는다.
- 시드 저장 방식은 패턴이 더 자연스럽지만 `TileData` 의 **4 byte 예산**(기획서 4.1)을 깬다.
  512×512 에서 1 byte = 256 KB 이고, 확산 잡은 매 틱 그리드를 통째로 훑으므로 크기가 곧 대역폭이다.
- 상태 저장이 없으니 EditMode 테스트로 확산 규칙을 정확히 검증할 수 있다 (CLAUDE.md 5 장 "테스트할 핵심 로직").

**주의로 남겨 둘 것**: 해시 품질이 나쁘면 확산이 격자 패턴으로 보인다. 다음 덩어리에서 눈으로 확인한다.

### 결정 3 — 지형 렌더: 화면 부근 타일만 엔티티 풀링

기획서 8.5 에는 **"512×512 Texture2D 에 상태를 기록해 풀스크린 쿼드 셰이더에서 샘플링"** 으로 적혀 있었다.
사용자 결정으로 **엔티티 풀링**으로 변경하고 기획서 8.5 를 갱신했다.

| | 텍스처 1 장 | **화면 부근 엔티티 풀 (선택)** |
|---|---|---|
| 드로우콜 | 1 | 1 (머티리얼 1 개 + 인스턴스별 색) |
| CPU 비용 | 틱마다 1 MB 업로드 | 프레임마다 ~1,200 쿼드 갱신 (병렬 잡) |
| 엔티티 수 | 1 | ~1,232 |
| M6 아트 교체 | 셰이더에 아틀라스 샘플링을 새로 짜야 함 | 쿼드에 스프라이트를 붙이면 끝 |

**선택 이유**: 드로우콜은 어차피 양쪽 다 1 개다. 갈라지는 건 **나중에 스프라이트·애니메이션을 넣을 때의 비용**이고,
그쪽이 엔티티 풀 압승이다. 대신 카메라가 움직일 때마다 쿼드를 갱신하는 비용을 진다.

**그 갱신 비용을 없앤 장치 — 창(window) 자리 고정 배정**:
풀의 i 번째 쿼드는 **항상** 창 안의 `(i % ViewWidth, i / ViewWidth)` 칸을 담당한다.
창이 움직이면 "어느 쿼드에 어느 타일을 줄지" 를 다시 푸는 대신, 모든 쿼드가 자기 자리의 타일을 다시 읽기만 한다.
배정 로직도, 들고 나는 타일 추적도, 자료구조도 없다 — **전부 인덱스 산술**.
처음엔 "화면에 들어온 타일에 쿼드를 배정하고 나간 타일은 반납" 하는 풀을 떠올렸는데,
그건 적·젬 풀의 사고방식을 습관적으로 가져온 것이었다. 타일은 **위치가 인덱스로 결정되는 고정 격자**라
개별 수명이라는 개념 자체가 없다. 1,200 개를 통째로 덮어쓰는 게 더 싸고 버그가 없다.

### 발사 규칙 (사용자 확정 — 제안안 A)
```
한 번 발사 = 조준 수 T × 타겟당 발 수 P
  T : 사거리 안 가까운 적 T 마리를 각각 노림 (적이 T 보다 적으면 가까운 적부터 반복)
  P : 타겟 방향 중심으로 [-F/2, +F/2] 에 고르게 배치
시작: 간격 0.15s, T=3, P=1, F=15° → 초당 약 20 발

레벨업 (최대치 도달 시 후보 제외)
  조준 +1 (≤12) / 투사체 +1 (≤7) / 부채꼴 +15° (≤90°) / 관통 +1 (≤10)
  폭발: 첫 선택 해금(반경 1.0, 피해 50%) → 이후 반경 +0.5 (≤3.0)
  + 기존 5 종 (피해 / 연사 / 탄속 / 이동속도 / 최대 HP)
```

### 왜 이렇게 했나

**1. "여러 적 조준" 과 "부채꼴" 을 곱으로 조합** (사용자 결정)
- 둘 다 "한 발사의 여러 발을 어디로 보내나" 를 정하는 규칙이라 충돌한다. 조준 수(타겟 분산)와 타겟당 발 수(부채꼴)를 **직교하는 두 축**으로 나눴다.
- **대안**: 부채꼴을 별도의 추가 사격으로 — 규칙이 두 갈래가 돼 강화 조합을 예측하기 어렵다.

**2. 한 프레임 여러 번 발사 + 상한 4**
- 기존 구조(프레임당 1 회)는 발사 간격이 프레임 시간보다 짧아지는 순간 **연사 속도가 FPS 에 묶인다** (60 FPS 면 초당 최대 60 회).
- 상한이 없으면 긴 프레임(로딩·에디터 멈춤) 뒤 수십 회를 몰아 쏜다. 상한에 걸려 밀린 발사는 **버린다** — 남기면 다음 프레임에도 계속 몰아 쏜다.
- 타겟은 프레임에 한 번만 찾는다 (같은 프레임의 발사들은 대상이 같다).

**3. 가까운 T 마리 탐색 — 정렬 삽입 + 고리 조기 종료**
- T ≤ 16 이라 힙보다 삽입 정렬이 싸다. `FixedList` 두 개(위치·거리)를 나란히 유지.
- 종료 조건: T 마리를 모았고, T 번째 거리가 다음 고리의 최소 거리(ring × 셀) 이하.

**4. 관통 — 명중 기록을 컴포넌트 안에 `FixedList128Bytes<Entity>`**
- **대안**: `DynamicBuffer<Entity>` — 버퍼 헤더 + 넘치면 힙 할당. / 기록 없이 관통 — 겹쳐 있는 동안 같은 적을 매 프레임 때린다.
- 15 칸이면 관통 상한 10 + 직격을 넉넉히 덮는다. 가득 차면 가장 오래된 기록부터 버린다.
- **풀 재사용 시 기록을 반드시 비운다** (발사 시 `HitHistory = default`). 안 비우면 지난 생애에 맞힌 적을 이번 생애에 못 맞힌다.
- 한 프레임에 한 마리만 맞힌다 — 탄이 프레임당 약 0.2 u 이동해 적 지름(0.5)보다 작으므로, 붙어 있는 적도 다음 프레임에 차례로 맞는다.
- 걸린 것: `FixedList.Contains` 는 `ref this` 확장이라 `in` 매개변수로 넘기면 CS8329. `ref` 로 변경.

**5. 폭발 — 직격 대상 제외, 적 위치 중심**
- 직격 대상은 직격 피해만 (폭발 피해 50% 를 "주변 피해" 로 명확히).
- 중심은 맞은 적의 위치 — 적 중심에서 퍼지는 게 시각적으로 자연스럽다 (폭발 연출은 M3).
- 반경 상한 3.0 — 조회 셀이 반경의 제곱으로 늘어난다 (3.0 → 9×9 = 81 칸).

**6. 최대치 도달 선택지 제외**
- 수치 강화 5 종은 상한이 없어 항상 후보 → 후보가 3 개 미만이 되는 일은 없다.

### 성능에 대한 예상 (측정 전 — 주장 아님)
- 발사가 메인 스레드라, 강화가 쌓이면(T=12 × P=7 = 84 발/회 × 초당 수 회) `EntityManager` 호출이 늘어난다. 프로파일러에서 `ShardFireSystem` 이 보이면 배치 방식을 바꾼다.

### 왜 이렇게 했나

**1. UI = uGUI** (사용자 결정, 프로젝트 전역) — UI Toolkit 은 다른 프로젝트에서 충분히 써봤다. 기획서 11장 미결 4 번에 대한 답.

**2. 드랍 = 항상 소형 1 개** (사용자 결정) — 적 1 종뿐인 M1 에 확률표는 과함. 젬 종류는 따로 두지 않고 **값(Value)** 으로 표현 → 합치기와 자연스럽게 맞물린다.

**3. 풀이 가득 차면 가장 먼 젬에 합치기** (사용자 결정 — 추천안(버리기)과 다르게 감)
- 경험치 손실이 없다. "가장 먼 젬" 은 풀이 바닥난 **프레임에 한 번만** 계산하고, 그 프레임 넘친 요청을 전부 몰아준다 — 드랍마다 다시 찾으면 O(드랍 × 젬).
- 배정은 **단일 잡**. 사망 잡(병렬)이 직접 빈 젬을 켜면 여러 워커가 같은 젬을 고르는 레이스.

**4. `PlayerPosition` 사본 도입**
- 젬 흡인 잡은 젬의 `LocalTransform` 에 **쓴다**. 같은 잡에서 플레이어 `LocalTransform` 을 룩업(읽기)하면 같은 타입 읽기+쓰기라 안전 검사에 걸린다.
- 메인 스레드에서 `LocalTransform` 을 읽으면 적 이동 잡을 기다린다. 사본은 메인 스레드에서만 쓰므로 기다릴 잡이 없다.

**5. 레벨업 — 판정·적용 분리, UI 는 "무엇을 골랐나" 만**
- 판정(`LevelUpSystem`)은 게임플레이 그룹 맨 앞, **지난 프레임** 경험치로 — 합산 잡이 끝나 있어 대기 없음 (`PlayerDeathSystem` 과 같은 패턴).
- 적용(`LevelUpApplySystem`)은 그룹 **밖** — Paused 동안 그룹이 멈춰 있으므로, 안에 두면 영원히 재개되지 않는다.
- UI 는 `SelectedIndex` 만 기록. 플레이어 컴포넌트 쓰기를 ECS 한 곳에 모아 적용 순서·동기화를 통제.
- 한 번에 1 레벨만. 두 레벨 분량이면 재개 다음 프레임에 다시 걸린다 → "남은 레벨업 수" 상태가 필요 없다.

**6. UI 데이터는 사본 싱글턴으로** (`PlayerStatusView`)

### 왜 이렇게 했나

**1. 최근접 탐색 범위 = 무기 사거리** (사용자 결정)
- **대안**: 거리 무관하게 가장 가까운 적 (기존 규칙) — 주변이 비면 스폰 반경(~40)까지 수천 칸을 훑는다.
- **선택 이유**: 닿지 않을 적에게 탄을 낭비하지 않고, 탐색 비용 상한이 생긴다. **게임 규칙이 바뀐 것** — 사거리 안에 적이 없으면 쏘지 않고 대기.

**2. 고리 탐색의 조기 종료**
- 고리 r 을 다 본 뒤, 다음 고리의 셀은 원점에서 **최소 r × 셀 크기** 떨어져 있다 (원점은 중심 셀 안 어딘가).
  이미 그보다 가까운 적을 찾았으면 멈춘다. 적이 가까우면 1~2 고리로 끝난다.
- 고리는 테두리만 돈다 — 가운데 행은 양 끝 두 칸만.

**3. `MaxAgentRadius` 가 필요한 이유**
- 적은 **중심 좌표의 셀**에만 들어간다. 반경이 큰 적은 옆 칸에 중심이 있어도 닿을 수 있어서, 조회 반경 + 적 최대 반경만큼 칸을 봐야 누락이 없다.
- 이전 분리 코드는 "상대도 나와 같은 크기" 로 가정했는데, 세 조회(분리·충돌·탐색)를 이 상수 하나로 통일했다. M4 에서 Blob 스탯 최대치로 교체.

**4. 발사 시스템을 적 이동보다 앞으로 옮김** (순서 변경)
- 발사 시 메인 스레드에서 `LocalTransform` 을 읽고 쓴다. 이전 순서(이동 **뒤**)에서는 적 이동 잡이 끝날 때까지 기다리는 **동기화 지점**이 발사 프레임마다 생겼다.
- 이동 **앞**이면 기다릴 것은 해시 재구축뿐이고, 그건 조회에 어차피 필요하다. 탐색 대상도 해시 스냅샷(이동 전)이라 순서가 맞는다.

**5. 해시 스냅샷이 1 프레임 이르다는 점**
- 충돌 판정이 **이동 전** 적 위치를 본다. 적 이동량은 프레임당 약 0.04 u 로 판정 반경 합(0.4)의 10% — 무시.

## 2026-09-17 (3) — [M1→M2 선행] 적 공간 해시 + 적끼리 분리 ✅

**커밋** `9ac3060` | **관련 이슈** 없음

> 상태: 코드 + 컴파일 + 사용자 플레이 확인 완료 (적 500).
> **마일스톤 순서 변경**: 사용자 요청으로 대시를 보류하고, M2 핵심 작업인 공간 해시·분리를 M1 도중에 앞당겼다.
> M1 의 나머지(XP·레벨업)는 그대로 남아 있다.

### 요청
"적이 몰려올 때 겹치지 않게 서로 피하게 하자. 전체를 읽으면 연산량이 감당 안 되니 자기 주변만 검사하자." (사용자)

### 한 일

| 파일 | 역할 |
|---|---|
| `Spatial/AgentRef.cs` | 해시 한 칸의 값 — 엔티티, 위치 **스냅샷**, 반경 |
| `Spatial/EnemySpatialHash.cs` | 싱글턴: `NativeParallelMultiHashMap<int, AgentRef>` + 빌드/조회 잡 핸들. 셀 크기 1.0 (기획서 8.3), 셀 좌표 → 키 헬퍼 |
| `Spatial/BuildEnemySpatialHashSystem.cs` | 매 프레임 비우고 살아있는 적을 **병렬로** 다시 채움 (기획서 8.2 의 6번) |
| `Enemy/EnemySeparation.cs` | 분리 설정 싱글턴: 강도 1.5, 이웃 검사 상한 16 |
| `Enemy/EnemySpawnerAuthoring.cs` (수정) | 분리 설정을 스포너에 베이킹 (씬 작업 불필요) |
| `Enemy/EnemyChaseSystem.cs` (재작성) | 추격 방향 + 이웃 밀어내기 합성. 자기 셀 ± 범위만 조회 |

**순서**: `EnemyRespawn → BuildEnemySpatialHash → (PlayerMove) → EnemyChase → ...`

**알고리즘** (적 1 마리 기준)
```
chase = 플레이어 방향 (길이 1, 도착 직전엔 남은 거리만큼 축소)
push  = Σ (나 - 이웃) 단위벡터 × (1 - 거리 / (내 반경 + 이웃 반경))   ← 겹친 이웃만, 최대 16 마리
dir   = chase + push × 1.5,  길이 1 로 상한
이동  = dir × 속도 × dt
```

### 왜 이렇게 했나

**1. 공간 해시 = MultiHashMap 먼저** (사용자 결정)

- **대안**: 카운팅 소트 그리드 (기획서의 최적화 2단계). 캐시 지역성이 좋아 2~3 배 빠르다고 예상되지만, 고정 월드 범위가 필요하고 코드가 복잡하다.
- **선택 이유**: 병렬 쓰기가 쉬워 코드가 단순. 나중에 그리드로 바꿀 때 **before/after 측정**이 면접 소재가 된다.
- 셀 키는 `math.hash(int2)`. 서로 다른 셀이 같은 키로 충돌할 수 있지만 조회 쪽이 거리로 다시 걸러 정확성에 영향 없다.
- `(int)` 캐스트가 아니라 `floor` 로 셀을 구한다 — `(int)(-0.5) == (int)(0.5) == 0` 이라 원점 주변 셀이 두 배 크기가 된다.

**2. 분리 = 밀어내는 힘 (보이드 separation)** (사용자 결정)

- **대안 A — 겹침 위치 보정**: 겹침은 확실히 없어지지만 상호 보정이라 병렬화하려면 스냅샷 + 반씩 밀기가 필요하고, 밀집 구간에서 떨림이 생기기 쉽다.
- **대안 B — 힘 + 깊은 겹침만 보정**: 품질은 가장 좋지만 조정할 수치가 늘어난다.
- **선택 이유**: 움직임이 부드럽고 **병렬화가 그대로 안전**하다.
- **알려진 한계**: 플레이어 주변처럼 사방에서 추격 힘이 모이면 약간 겹칠 수 있다 — 강도(1.5)로 조절.

**3. 병렬 안전성 — 스냅샷을 해시에 복사**

- 이웃 위치를 `ComponentLookup<LocalTransform>` 으로 읽으면, 같은 잡이 자기 `LocalTransform` 에 쓰는 것과 충돌해 `ScheduleParallel` 이 불가능하다.
- 해시에 위치를 복사해 두면 "이웃은 해시에서 읽고, 쓰기는 자기 것만" → 2026-09-16 에 기록한 "분리를 넣는 순간 병렬화가 깨진다" 는 우려를 이 방식으로 피했다.
- 대가: 이웃의 **이번 프레임 이동을 모른 채** 피한다 (1 프레임 늦은 정보). 체감 불가.

**4. 해시 컨테이너의 잡 의존성을 직접 관리**

- 컨테이너가 컴포넌트 안에 있어 ECS 자동 의존성 추적이 닿지 않는다. `DamageEventBus` 와 같은 패턴으로 핸들 두 개를 둔다.
  - `BuildHandle` — 추격 잡이 재구축 완료 뒤에 돌도록
  - `ReadersHandle` — 다음 프레임 `Clear()` 전에 지난 프레임 조회 잡을 끝내도록
- 병렬 쓰기는 용량을 못 늘려서 `Capacity` 를 미리 확보. 개수는 `CalculateEntityCountWithoutFiltering()` (풀 전체 = 상한) — 필터를 쓰면 enabled 비트 때문에 동기화 지점이 생긴다.

**5. 세부 결정**

- **분리 반경 = 두 적의 `HitRadius` 합** — 별도 수치를 두지 않았다. 기획서 `AgentRef` 에 `Radius` 가 있는 이유도 이것.
- **검사 셀 범위를 계산** (`ceil(내 반경 × 2 / 셀 크기)`) — 반경을 키워 셀보다 커져도 이웃을 놓치지 않게. 현재 값(0.25)에서는 ±1 = 9 칸.
  "상대 반경도 나와 같다" 는 M1 가정이 들어 있다 — 적 크기가 달라지는 M4 에서 재검토.
- **이웃 16 마리 상한** — 밀집 구간 최악 비용을 자른다. 가까운 순이 아니라 발견 순이라 정밀도는 약간 희생.
- **완전히 같은 위치** — 재스폰 직후·플레이어 중심에서 실제로 생긴다. 두 적이 **반대 방향**을 받도록 엔티티 쌍의 해시로 각도를 정하고 인덱스 크기로 부호를 나눴다. 각자 난수를 쓰면 같은 쪽으로 밀려 계속 붙어 있을 수 있다.
- **최종 방향 길이 1 상한** — 밀리는 적이 자기 속도보다 빨리 튀어나가지 않게.
- **플레이어는 밀지 않는다** — 적끼리만 피한다. 적은 여전히 플레이어 중심을 향하므로, 플레이어 주변에 원형으로 뭉친다.

**6. 기존 전수 비교는 이번에 바꾸지 않음** (사용자 결정)

- 투사체 충돌·최근접 탐색은 전수 비교 그대로. **먼저 현 상태 성능을 측정**해 기준선을 남기고, 다음 덩어리에서 해시 조회로 교체 → 재측정.

### 왜 이렇게 했나

**1. 플레이어를 MonoBehaviour 가 아니라 엔티티로**

- **선택**: 플레이어도 엔티티. 매니지드 코드는 입력 읽는 시스템 하나뿐
- **대안**: (a) 하이브리드 — GameObject + SpriteRenderer + Animator (b) M1 은 하이브리드로 가고 M3 에 전환
- **논의 과정**: "외부 2D 스프라이트 에셋을 쓸 거면 하이브리드가 편하지 않나"라는 질문이 나왔고,
  이건 타당한 지적이었다. 하지만 **적 1만 마리도 스프라이트**라는 점이 계산에서 빠져 있었다.
  `SpriteRenderer` 는 Entities Graphics 에서 못 쓰므로 적·투사체·젬은 어차피
  **아틀라스 + 쿼드 + 머티리얼 프로퍼티 UV 오프셋** 경로를 만들어야 한다(기획서 8.5).
  그 경로를 만들고 나면 플레이어는 같은 경로를 공짜로 쓴다.
  즉 "스프라이트를 쓴다"는 사실 자체는 하이브리드의 근거가 되지 못한다.
- **선택 이유 (결정적)**: **지형 시스템**. 기획서상 플레이어는 연소 타일에서 피해를 받고,
  빙판에서 이동속도가 바뀌고, 균열에서 속도가 변한다. 이게 전부 타일 그리드 잡 안에서 일어나는데
  플레이어만 GameObject 면 **이 판정을 플레이어용으로 한 번 더 따로 짜야 한다.**
  부차적으로, 하이브리드는 BRG 엔티티와 SpriteRenderer 라는 **렌더 경로 2개**가 생겨
  둘 사이의 앞뒤 정렬(렌더 큐 vs Sorting Layer)이 까다로워진다.
- **포기한 것**: `Animator` 와 애니메이션 편집 워크플로우. 플레이어 애니메이션을 UV 프레임 인덱스로
  직접 계산해야 한다. 뱀서라이크 플레이어는 보통 idle/walk 몇 프레임 + 좌우 반전 + 피격 플래시라
  감당 가능하다고 판단.
- **탈출구**: Entities 에 `Unity.Entities.Hybrid.HybridComponents` (Companion GameObject) 가 있다.
  애니메이션이 정말 복잡해지면 **플레이어 1개에만** GameObject 를 붙여 `Animator` 를 쓸 수 있다.
  1만 개에 쓰면 망하지만 1개는 비용이 무의미하다. **되돌리기 어려운 결정이 아니다.**

**2. 입력만 SystemBase, 나머지는 전부 ISystem + Burst**

- **선택 이유**: `InputActionAsset` / `InputAction` 은 매니지드 클래스라 Burst ISystem 에서 다룰 수 없다.
  매니지드 경계를 **이 시스템 하나로 격리**하고, 읽은 값을 싱글턴 컴포넌트에 써두면
  이후 모든 게임플레이 시스템은 Burst 로 컴파일된 채 그 값을 읽는다.
  플레이어를 엔티티로 둔 이유(동기화 경계 최소화)가 실제 구조로 구현된 지점.

**3. 새 Input Actions 를 만들지 않고 기존 `Player/Move` 재사용**

- 프로젝트에 `InputSystem_Actions.inputactions` 가 이미 전역 액션으로 설정돼 있었고
  `Player/Move` 가 Vector2 + WASD 로 구성돼 있어 그대로 썼다. API 존재 여부(`InputSystem.actions`,
  `InputActionAsset.FindAction`)는 패키지 소스에서 직접 확인한 뒤 사용.

**4. 대각선 정규화를 입력 단계에서**

- WASD 는 (1,1) 이 들어와 길이가 √2 가 된다. 정규화하지 않으면 대각선이 41% 빠르다.
- **길이가 1 을 넘을 때만** 정규화한다. 게임패드 아날로그 스틱은 살짝 기울인 상태의 길이가
  1 미만인데, 무조건 정규화하면 미세 조작이 전부 최대 속도가 되어버린다.

**5. 플레이어를 싱글턴이 아니라 Query 로 순회**

- 플레이어는 1 개지만 `SystemAPI.Query` 로 돈다. 싱글턴으로 강제하면 나중에 구조를 바꿔야 하고,
  1 개짜리 순회는 비용이 사실상 0 이다.

**6. 카메라는 MonoBehaviour 유지**

- 카메라는 Unity 매니지드 오브젝트라 어차피 GameObject 다. 중요한 건 이게 **ECS 를 읽기만 하는
  단방향**이라는 점 — 양방향 동기화 버그가 생길 여지가 없어 "플레이어를 엔티티로" 결정과 충돌하지 않는다.

**2. 목표 밀도 1만 + M2를 게이트로 설정**

- **선택**: M2(공간 해시·풀링·인스턴싱 렌더로 적 1만 @60fps)를 통과하기 전엔 M3 이후 콘텐츠를 만들지 않는다
- **선택 이유**: 성능 뼈대(풀링, 공간 해시, 단일 아키타입)는 **나중에 끼워넣는 비용이 압도적으로 크다.** 콘텐츠를 먼저 쌓은 뒤 성능이 안 나오면 전부 다시 써야 한다.
- **포기한 것**: 초반에 눈에 보이는 결과물이 적어 동기 부여가 떨어짐 → M1에서 적 1,000 규모의 플레이 가능한 루프를 먼저 만들어 완화.
- **분기 계획**: M2 미달 시 목표 밀도를 3,000으로 낮추고 기획 재조정 (기획서 10장에 명시)

**3. Unity Physics 미사용 결정**

- **선택**: 물리 패키지를 설치하지 않고 공간 해시 기반 원-원 겹침 판정을 직접 구현
- **대안**: Unity Physics (`com.unity.physics`) 사용
- **선택 이유**: 2D 원-원 판정만 필요한데 Unity Physics는 월드 빌드 + 브로드페이즈 + 내로우페이즈 전체 파이프라인 비용을 지불해야 한다. 1만 유닛에서 감당이 안 될 것으로 판단.
- **포기한 것**: 검증된 물리 구현을 버리고 직접 만들게 됨 → 버그 리스크. 단 판정 종류가 원-원 하나뿐이라 감당 가능한 범위로 봄.
- **⚠ 미검증**: 이건 **아직 실측으로 확인한 게 아니라 판단**이다. M2에서 자체 구현 공간 해시의 실제 수치를 측정해 이 결정이 옳았는지 검증 필요.

**4. 적을 단일 아키타입으로 설계**

- **선택**: 적 6종 전부 하나의 아키타입. 차이는 `EnemyTypeId(byte)` + Blob 스탯 테이블로 분기
- **대안**: 적 타입별로 다른 컴포넌트 조합 = 다른 아키타입
- **선택 이유**: ECS는 아키타입 단위로 청크가 나뉜다. 타입별로 아키타입을 나누면 청크가 파편화되어 순회 시 캐시 효율이 무너지고, 청크 하나가 절반만 차는 상황이 속출한다.
- **포기한 것**: 타입별 고유 컴포넌트를 못 쓰므로 모든 적이 안 쓰는 필드까지 들고 다님 (메모리 낭비). 대신 컴포넌트를 작게 유지(적 1개당 ≤64byte 목표)해서 상쇄.
