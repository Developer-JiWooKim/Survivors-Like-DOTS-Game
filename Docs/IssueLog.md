## 이슈 상세

### ISSUE-001

| | |
|---|---|
| **발생일시** | 2026-09-16 |
| **마일스톤** | M-1 (기획) |
| **분류** | 툴링 |
| **상태** | ✅ 해결 |
| **해결일** | 2026-09-16 |
| **소요 시간** | 수 분 |
| **관련 작업** | [WorkLog 2026-09-16](WorkLog.md#2026-09-16--m-1-프로젝트-기획-및-작업-지침-수립) |
| **관련 커밋** | - |

**증상**

Bash heredoc(`cat > file <<'DOC' ... DOC`)으로 기획서 마크다운을 작성하자 파일이 생성되지 않고 셸 에러 발생.

```
/usr/bin/bash: -c: line 1: unexpected EOF while looking for matching `''
```

**재현 조건**

마크다운 본문에 코드 블록 백틱(```` ``` ````), 인라인 코드, 따옴표가 다량 포함된 긴 문서를 heredoc으로 작성할 때.

**원인**

`<<'DOC'` 로 따옴표를 감싸 변수 확장은 막았으나, 명령 전체가 `&&` 체인으로 한 줄에 전달되는 과정에서 본문 내 따옴표가 셸 파싱 단계에서 인용 부호로 해석됨.

**시도한 것**

| 시도 | 결과 |
|---|---|
| `<<'DOC'` 인용 heredoc | 실패 (동일 에러) |
| Write 파일 쓰기 도구로 전환 | ✅ 성공 |

**해결**

긴 마크다운/코드 파일 생성은 셸 heredoc 대신 파일 쓰기 도구를 사용.

**재발 방지**

- 여러 줄 마크다운·C# 코드 파일은 **항상** 파일 쓰기 도구로 생성한다.
- 셸은 파일 조회·검색·git 등 명령 실행 용도로만 사용한다.

**재발 기록 — 2026-09-17 (M1 파편탄 작업)**

위 재발 방지 규칙을 어기고 C# 파일 5 개를 **한 번의 bash 호출에 heredoc 여러 개로** 작성하려다 같은 에러가 났다.

```
/usr/bin/bash: -c: line 163: unexpected EOF while looking for matching `''
```

- bash 가 스크립트 **전체를 먼저 파싱**하다 실패하므로, 파일이 하나도 쓰이지 않았다 (부분 적용 없음 — 그나마 다행).
- 같은 호출 앞부분의 `sed` 한 줄도 실행되지 않았다.
- Write 도구로 파일별로 다시 작성해 해결. 직전 호출(heredoc 7 개)은 성공했기 때문에 "되는구나" 하고 규칙을 느슨하게 적용한 것이 원인.
- 추가로 알게 된 것: 이 환경에는 **Python 이 없다** (`python` 이 MS Store 안내를 출력). 파일 일부 치환을 파이썬으로 하려던 시도도 실패했다.
- **규칙 재확인**: 코드·문서 생성은 Write/Edit 도구. 셸 heredoc 은 쓰지 않는다.

### ISSUE-002

| | |
|---|---|
| **발생일시** | 2026-09-16 ~15:59 |
| **마일스톤** | M0 |
| **분류** | 툴링 |
| **상태** | ⚠️ 미해결 (재현되지 않음, 관찰 기록) |
| **해결일** | - |
| **관련 작업** | [WorkLog 2026-09-16 (M0)](WorkLog.md#2026-09-16--m0-unity-cli-검증-파이프라인-구축) |
| **관련 커밋** | - |

**증상**

`Tools/unity-test.sh EditMode` 최초 실행 시 스크립트가 **exit 255** 로 종료. `[*] EditMode 테스트 실행 중...` 이후 스크립트의 결과 출력 블록이 **전혀 실행되지 않음**.

그런데 Unity 쪽 로그는 정상 종료였다:

```
Test run completed. Exiting with code 0 (Ok). No tests were executed.
```

결과 XML(`Logs/test-results-EditMode.xml`, 750 byte)도 정상 생성되어 있었다.

**재현 조건**

재현되지 않음. 동일 명령을 재실행하니 정상 동작하고 exit 0 반환.

| 실행 | 결과 |
|---|---|
| 1회차 (asmdef 추가 직후) | exit 255, 스크립트 후처리 미실행 |
| 2회차 (동일 명령) | exit 0, 정상 출력 |

**원인**

미파악. 가설:
- Unity 배치모드 프로세스가 종료되는 과정에서 호출 측 셸 세션이 영향을 받음
- 1회차는 새 asmdef 임포트가 겹쳐 실행 시간이 길었음 → 타이밍 의존 가능성

**시도한 것**

| 시도 | 결과 |
|---|---|
| Unity 로그 확인 | Unity 자체는 exit 0 정상 종료 확인 |
| 결과 XML 존재·내용 확인 | 정상 생성됨 (`total="0"`) |
| XML 파싱 로직 단독 실행 | 정상 동작 (grep/wc 모두 정상) |
| 동일 명령 재실행 | ✅ 정상 (exit 0) |

→ **스크립트 로직과 Unity 양쪽 모두 문제없음을 확인.** 셸 프로세스 종료 경로 문제로 추정.

**해결**

미해결. 현재는 재실행으로 우회 가능.

**재발 방지 / 대응 방침**

- `unity-test.sh` 가 **출력 없이** 비정상 종료하면, 원인을 파고들기 전에 **`Logs/test-results-*.xml` 과 Unity 로그를 먼저 확인**한다. Unity 쪽이 정상이면 셸 문제이므로 재실행한다.
- 재발이 잦아지면 스크립트를 `run_in_background` 로 돌리거나 Unity 호출과 결과 파싱을 별도 명령으로 분리하는 것을 검토한다.
- **반복되면 상태를 🔁 재발 로 바꾸고 원인을 다시 판다.**

### ISSUE-003

| | |
|---|---|
| **발생일시** | 2026-09-16 |
| **마일스톤** | M0 |
| **분류** | 툴링 |
| **상태** | ✅ 해결 |
| **해결일** | 2026-09-16 |
| **관련 작업** | [WorkLog 2026-09-16 (M0)](WorkLog.md) |

**증상**

`BenchmarkSceneBuilder.cs` 의 asmdef 참조 누락으로 컴파일이 실패했는데, `unity-check.sh` 가 에러 요약을 출력하지 않고 "Unity 가 비정상 종료했습니다" 라는 일반 메시지만 띄웠다. 실제 에러는 로그 안에 있었다.

```
error DC0061: Assembly Assets.MyAssets.Scripts.Editor relies on Unity.Entities
which uses the Unity.Collections AllocatorHandle type but does not have a
reference to Unity.Collections.
```

**재현 조건**

Roslyn 표준 `CS####` 가 아닌 진단 코드로 컴파일이 실패할 때. 항상 재현된다.

**원인**

`unity-check.sh` 의 에러 추출 정규식이 `error CS[0-9]+` 로 **접두사를 `CS` 로 가정**하고 있었다.
DOTS 소스 제너레이터는 `DC####`, Burst 는 `BC####`, Unity 분석기는 `UNT####` 를 쓴다.
DOTS 프로젝트에서는 오히려 이쪽 에러가 더 자주 난다.

**시도한 것**

| 시도 | 결과 |
|---|---|
| 로그를 직접 열어 확인 | 에러는 로그에 정상 기록되어 있었음 → 스크립트 파싱 문제로 특정 |

**해결**

접두사를 가정하지 않고 파일·줄 정보까지 포함해 추출하도록 변경.

```bash
ERRORS=$(grep -oE "[^ ]+\.cs\([0-9]+,[0-9]+\): error [A-Z]+[0-9]+: .*" "$LOG" | sort -u)
```

**재발 방지**

- 로그 파싱은 **관측한 한 가지 형식에 맞추지 말고** 범용 패턴을 쓴다.
- 검증 스크립트가 "실패했다"고만 하고 이유를 못 대면, 그건 스크립트의 결함으로 취급한다.

### ISSUE-004

| | |
|---|---|
| **발생일시** | 2026-09-16 |
| **마일스톤** | M0 |
| **분류** | 성능 |
| **상태** | ✅ 해결 |
| **해결일** | 2026-09-16 |
| **관련 작업** | [WorkLog 2026-09-16 (M0)](WorkLog.md) |

**증상**

M0 첫 벤치마크(엔티티 10,000) 측정 결과, 드로우콜·배치 수가 0 으로 보고됐다.

```
FPS   203.7  (4.91 ms)
Main  5.13 ms
Ents  10006
Batch 0        ← 0
Draw  0        ← 0
SetPs 10
```

`Batch 0` / `Draw 0` 인데 `SetPass 10` 은 논리적으로 모순이다. 아무것도 안 그렸다면 SetPass 도 0 이어야 한다.
**즉 렌더가 실제로 몇 개의 드로우콜로 처리됐는지 알 수 없는 상태**이고, 이 값이 M0 의 핵심 확인 사항(인스턴싱이 먹었는가)이다.

**재현 조건**

에디터 플레이 모드, URP(Universal Renderer), `PerfOverlay` 의 `ProfilerRecorder` 로 측정.

**원인 (가설, 미확정)**

`ProfilerCategory.Render` 의 `"Draw Calls Count"` / `"Batches Count"` 는 빌트인 렌더 파이프라인용 카운터로 보이며,
SRP(URP) 에서는 값이 채워지지 않는 것으로 추정된다. `"SetPass Calls Count"` 만 동작한 정황이 이를 뒷받침한다.

**시도한 것**

| 시도 | 결과 |
|---|---|
| `ProfilerRecorder(ProfilerCategory.Render, "Draw Calls Count")` | 0 반환 (Valid 는 true) |
| `ProfilerRecorder(ProfilerCategory.Render, "Batches Count")` | 0 반환 |
| `ProfilerRecorder(ProfilerCategory.Render, "SetPass Calls Count")` | 10 반환 (정상 동작) |

| `UnityStats.batches` 사용 시도 | ❌ Unity 6 에서 제거된 멤버 (`error CS0117`). `UnityEditor.dll` 을 직접 뒤져 실존 멤버 확인 |
| `UnityStats.drawCalls` / `triangles` | ✅ 정상 동작 (16 / 40252) |
| `UnityStats.instancedBatchedDrawCalls` | ❌ **0 반환** — 이게 핵심 단서였다 |
| Game 뷰 Statistics 창 확인 | ✅ `Draw Calls : 16 (20004 instances)` — 여기서만 인스턴스 수가 보임 |

**원인 (확정)**

두 개의 별개 문제가 겹쳐 있었다.

1. **ProfilerRecorder 의 `Draw Calls Count` / `Batches Count` 는 URP(SRP) 에서 채워지지 않는다.**
   `SetPass Calls Count` 만 동작한 것이 단서였다. → 에디터에서는 `UnityStats` 로 우회.

2. **`instancedBatchedDrawCalls` 가 0 인 것은 버그가 아니라 정상이다.**
   이 카운터는 **구형 GPU Instancing(MeshRenderer 경로)** 을 센다.
   Entities Graphics 는 **BatchRendererGroup(BRG)** 이라는 완전히 다른 경로로 그리기 때문에
   여기에 집계되지 않는다.

**해결**

- 에디터에서는 `UnityStats.drawCalls` / `setPassCalls` / `triangles` 를 오버레이에 표시.
- **BRG 인스턴싱 여부를 판정하는 기준은 `instancedBatchedDrawCalls` 가 아니라
  "드로우콜 수 대비 엔티티 수" 다.** 엔티티 10,002 개가 드로우콜 16 개로 나왔으므로 인스턴싱은 정상 동작.
- 정확한 인스턴스 수는 Game 뷰 Statistics 창의 `Draw Calls : N (M instances)` 에서 읽는다.

**재발 방지**

| 시도 | 결과 |
|---|---|
| Editor.log 에서 예외 원문·스택 추출 | `CameraFollow.cs:57` 로 지점 특정 |

**해결**

- 앞으로 ECS ↔ MonoBehaviour 경계가 늘어나면 같은 문제가 반복된다.
  경계를 늘리지 않는 것이 최선이고, 그게 플레이어를 엔티티로 둔 이유이기도 하다.

`UnlitMaterialBuilder.Create` 가 새로 만들든 기존 것을 불러오든 `SetColor` 를 무조건 호출했다.

**시도한 것**

| 시도 | 결과 |
|---|---|
| `git diff` 로 의도치 않은 변경 발견 → `git checkout -- EnemyQuad.mat` 으로 커밋 상태 복구 | ✅ |
| 빌더 수정: 색은 **새로 만들 때만** 칠하고, 인스턴싱 플래그는 기존 머티리얼에도 강제 | ✅ |

**해결**

위 수정. 성능에 영향을 주는 설정(GPU Instancing)만 코드가 강제하고, 보이는 모양은 최초값만 준다.

**재발 방지**

### ISSUE-011

| | |
|---|---|
| **발생일시** | 2026-09-17 (M1 게이트 정리 중 코드 리뷰로 발견 — 증상 관측 전) |

| **해결일** | 2026-09-17 |

**증상**

플레이에서 관측된 적은 없다. 조회 코드를 테스트 가능하게 옮기다가 **논리적으로** 발견했다.
공간 해시 셀 키가 `(int)math.hash(int2)` 라 **서로 다른 두 셀이 같은 키**를 가질 수 있다. 그러면 한 버킷에 두 셀의 적이 섞이고,
**여러 칸을 도는 조회**가 두 셀을 모두 보면 같은 적을 두 번 만난다.

| 조회 | 결과 |
|---|---|
| 최근접 N 마리 (`ShardFireSystem`) | 같은 적이 타겟 목록에 2 번 → 탄이 한 적에게 몰림 |
| 폭발 (`ProjectileHitJob.Explode`) | **한 적이 폭발 피해를 2 번** 받음 |
| 분리 (`ChaseJob`) | 같은 이웃에게 2 배로 밀림 |
| 겹침 1 개 찾기 (`TryFindOverlap`) | 영향 없음 (하나만 찾고 끝) |

**재현 조건**

탐색 범위 안의 두 셀 키가 충돌할 때. 81 칸(폭발 최대) 중 충돌 확률은 낮지만 0 이 아니고, 매 프레임 수백 번 조회하므로 언젠가 발생한다.
**이런 버그는 플레이로는 거의 안 보인다** — "가끔 한 적이 좀 더 빨리 죽는다" 수준.

**원인**

`EnemySpatialHash.KeyOf` 주석에 "충돌해도 조회 쪽이 거리로 다시 거르므로 정확성에 영향 없다" 고 적었었다.
**한 칸만 볼 때는 맞지만, 여러 칸을 도는 조회에서는 틀린 가정**이었다 — 거리 검사는 "가까운가" 만 보지 "이미 셌나" 는 보지 않는다.

**시도한 것**

| 시도 | 결과 |
|---|---|
| `EnemySpatialHash.IsInCell(agent, cell)` 추가 — 버킷에서 나온 적의 실제 셀이 지금 보는 셀과 같을 때만 처리 | 세 조회에 적용 |
| 테스트 `FindNearest_DoesNotDuplicateOnHashKeyCollision` — 같은 적을 다른 셀 버킷에도 넣어 충돌을 흉내 냄 | ✅ 통과 |
| **뮤테이션 확인**: 방어를 잠시 끄고 같은 테스트 실행 | ❌ `Expected: 1 But was: 2` → 테스트가 버그를 실제로 잡는다는 것 확인 후 복구 |

**해결**

위 방어. 비용은 적마다 floor 2 번 + 비교 — 조회 비용 대비 무시할 수준.

**재발 방지**

- 해시 키가 원본 키(셀 좌표)와 1:1 이 아니면, **버킷에서 꺼낸 값이 정말 그 키의 것인지** 확인한다.
- 대안으로 셀 좌표를 충돌 없는 정수로 인코딩(예: `(x + 오프셋) * 폭 + y`)하는 방법이 있다 — 월드 범위 고정이 필요해 카운팅 소트 그리드(M2 최적화 2 단계)로 갈 때 함께 본다.
- 주석의 "정확성에 영향 없다" 같은 단정은 **어떤 사용 패턴에서** 참인지까지 적는다.

### ISSUE-012

| | |
|---|---|
| **발생일시** | 2026-09-18 (M3 덩어리 2 연소 확산, 사용자 육안 검증 중 발견) |
| **마일스톤** | M3 |
| **분류** | 게임로직 |
| **상태** | ✅ 해결 |
| **해결일** | 2026-09-18 |
| **관련 작업** | [WorkLog 2026-09-18 (2) 연소 확산](WorkLog.md) |

**증상**

사용자 확인 4 번 항목("물·바위에서 멈추는가") 검증 중 발견.

- 바위: 정상. 바위 위에서 G(기름)를 눌러도 기름이 덮이지 않는다.
- 물: **기름이 덮인다.** 물을 부분적으로 덮은 상태에서 불을 붙이면 물 쪽으로 번지지 않아 정상으로 보이지만,
  **물을 완전히 덮도록 기름을 바르고 불을 붙이면 물 타일이 통째로 사라진다** (다 탄 뒤 흙이 됨).

**재현 조건**

항상. 물 타일 위에 기름을 칠하고(현재는 디버그 G 키, 앞으로는 기름통 무기) 점화하면 재현된다.

**원인**

두 단계가 겹쳤다.

1. 기름을 칠할 때 타일을 **덮어쓴다** — `TileData.Of(TileType.Oil, 200)` 로 통째로 교체한다.
   이 시점에 이미 물이라는 정보가 사라진다. (바위만 예외 처리되어 있었다.)
2. 연소가 끝나면 기획서 4.3 대로 `Type = 흙` 이 된다. 원래 물이었는지 알 방법이 없다.

근본 원인은 **`TileData` 에 "원래 무엇이었나" 를 담을 자리가 없다**는 것이다.
4 byte 예산(기획서 4.1) 안에 Type 은 하나뿐이고, 기름은 그 자리를 빼앗는 방식으로 구현되어 있다.

**왜 그냥 두면 안 되나**

물은 기획서 4.2·4.3 에서 **방화선이자 감전 매개**다. 감전 콤보(전격 사슬 → 물 덩어리 전체)와
빙판 생성(물 + 냉기)의 전제이기도 하다. 기름 한 번으로 호수를 영구히 없앨 수 있으면
**지형을 비가역적으로 소모하는 최적 전략**이 생기고, 기획서 4.4 의 안전장치(비행 적)와 무관하게
지형 시스템 자체가 런 후반에 흙바닥만 남는 방향으로 수렴한다.

**시도한 것**

규칙 자체가 기획서 미명시라 고치기 전에 **선택지를 정리해 사용자 판단을 받았다** (CLAUDE.md 2 장).

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | 기름이 물 위에 뜨고, 다 타면 물로 복귀 | 타일 종류 1 개 증가 + 분기. 물의 역할·콤보 모두 유지 |
| B | 기름을 물에 못 부음 (바위처럼 제외) | 코드 가장 단순. **물을 다리 삼아 불을 잇는 플레이가 불가**, 유정공이 물 많은 구역에서 무력 |
| C | 현상 유지 (물 소모가 의도된 규칙) | 코드 변경 0. 기획서 4.2·4.3 을 고치고 감전·빙판 빌드 밸런스를 다시 잡아야 함 |

**사용자 결정 (2026-09-18): A.**

**시도한 것**

| 시도 | 결과 |
|---|---|
| `TileData` 에 "원래 타입" 필드 추가 | ❌ 검토 단계에서 기각 — 4 byte 예산(기획서 4.1)을 깬다. 512×512 에서 1 byte = 256 KB 이고 확산 잡이 매 틱 전체를 훑는다 |
| **`TileType.OilOnWater` 를 별도 종류로 추가** | ✅ Type 값 하나를 더 쓰는 것으로 같은 정보를 표현. 메모리 증가 0 |

**해결**

1. `TileType.OilOnWater = 7` 추가.
2. `BurnRules.Step` — 연료가 0 이 될 때 `OilOnWater` 만 `Water` 로, 나머지는 기획서 4.3 대로 `Dirt` 로.
3. `TileTypes.IsOil` / `IsWaterLike` 헬퍼 — 확산 확률 3 배는 두 기름 모두에, 앞으로 들어올
   감전 flood fill 과 동결은 물 위 기름도 물로 보게 한다 (전격·냉기 콤보 유지).
4. 기름을 칠할 때 바닥이 물이면 `OilOnWater` 로 (`DebugTerrainPaintSystem`, 앞으로의 기름통 무기도 동일 규칙).
5. 색: 기름(거의 검정)에 물의 파랑을 섞어, 불을 붙이기 **전에** 아래가 물임을 알아보게 했다.

테스트 5 개 추가 (총 44/44 통과). 그중 `OilOnWater_LakeSurvivesBeingFullyCovered` 는
**사용자가 관측한 재현 절차 그대로** — 물을 완전히 덮고 태운 뒤 물이 한 칸도 빠짐없이 돌아오는지 본다.

**재발 방지**

- **타일 종류를 묻는 분기를 `TileTypes` 헬퍼로 모았다.** 종류가 늘 때(빙판·균열·오염) 분기를
  여러 파일에 흩뿌리면 이번과 같은 누락이 반복된다.
- 교훈: **"덮어쓰기" 는 정보를 지우는 연산이다.** 지형처럼 되돌아와야 하는 상태를 덮어쓸 때는
  "무엇을 잃는가" 를 먼저 묻는다. 여기서는 바위만 예외 처리하고 물을 빠뜨렸다.
- 이 버그는 **테스트가 아니라 육안 검증이 잡았다.** 규칙 테스트는 "기름이 탄다" 를 확인했지
  "기름 아래 무엇이 있었나" 는 묻지 않았다. 확인 항목을 단계로 적어 사용자에게 넘긴 절차가 값을 했다.

### ISSUE-013

| | |
|---|---|
| **발생일시** | 2026-09-18 (M3 덩어리 5 지형 이동 효과, 사용자 육안 검증 중 발견) |
| **마일스톤** | M3 |
| **분류** | 게임로직 |
| **상태** | ✅ 해결 |
| **해결일** | 2026-09-18 |
| **관련 작업** | [WorkLog 2026-09-18 (5) 지형 이동 효과](WorkLog.md) |

**증상**

바위 통과 불가를 넣은 뒤, 확인 3 번("적이 바위를 끼고 돌아 플레이어에게 오는가")에서 발견.

> "돌아오지 않고 플레이어를 향해서 계속 오려고 하는데 벽에 막혀서 오지 못하면 계속 끼어있음"

스크린샷상 적들이 바위 뒤로 **방사형 줄무늬**를 이루며 쌓여 있다. 바위가 만든 그림자 영역에
적이 도달하지 못하고 벽면에 눌린 채 정지한다.

**재현 조건**

항상. 적과 플레이어 사이에 바위가 있고, **적의 추격 방향이 벽면에 수직에 가까울 때**.

**원인**

`TerrainMovement.SlideAlongWalls` 는 x 이동과 y 이동을 따로 시험해 막힌 축만 버린다.
적이 바위를 **정면으로** 마주하면 추격 방향이 한 축에 몰리므로(예: 순수 +x),
막힌 축을 버리고 나면 **남는 이동량이 0** 이다. 어느 쪽으로도 못 간다.

비스듬히 부딪힐 때는 다른 축이 살아 있어 미끄러지지만(확인 2·4 번이 통과한 이유),
미끄러지다 보면 결국 벽면에 수직인 자세가 되어 거기서 멈춘다.

**즉 축 분리 미끄러짐은 "충돌 해소" 이지 "우회" 가 아니다.**
장애물을 돌아가려면 **어느 쪽으로 돌지 정하는 판단**이 필요한데, 현재 적에게는 그게 없다
(경로탐색 없는 직진 추격 — 기획서 6.1 의 추격형 정의).

**판단 착오 기록**

덩어리 5 에서 "막히면 정지" 대신 미끄러짐을 고른 근거가 **"바위 뒤의 적이 영영 도달하지 못한다"** 였다.
그 문제의식은 맞았으나, **축 분리 미끄러짐이 그것을 해결한다고 본 것이 틀렸다.**
미끄러짐은 정면 충돌을 해결하지 못하므로 같은 문제가 그대로 남는다.
확인 항목에 "적이 바위를 끼고 돌아오는가" 를 넣어둔 덕에 바로 드러났다.

**시도한 것**

| 시도 | 결과 |
|---|---|
| 축 분리 미끄러짐 (`SlideAlongWalls`) | 🔄 부분 해결 — 비스듬한 충돌은 해소, **정면 충돌은 여전히 끼임** |
| **흐름장 (BFS)** | ✅ 해결 — 아래 |

**해결**

**흐름장(flow field)** — 플레이어에서 출발하는 BFS 로 맵 전체의 "플레이어로 가는 방향" 을 한 번에 구하고,
적은 자기 칸의 방향을 **배열 읽기 1 회**로 가져다 쓴다.

**왜 A\* 가 아닌가 (사용자 질문에 답하며 정리)**

A\* 는 **출발지 1 → 목적지 1** 을 푼다. 적 10,000 마리에 쓰면 1 만 번 돌려야 하는데
**그 1 만 개의 경로가 전부 같은 곳(플레이어)으로 수렴**한다 — 같은 답을 1 만 번 다시 계산하는 셈이다.
흐름장은 방향을 뒤집어 목적지에서 맵 전체로 한 번 퍼뜨린다. **A\* 를 버린 게 아니라 목적지가 같은
A\* 1 만 개를 한 번에 푼 것**이다.

| | A\* | 흐름장 |
|---|---|---|
| 계산 단위 | 적 1 마리당 | 맵 1 장당 |
| 총량 (재계산 1 회) | 10,000 × 수백 노드 = 수백만 노드 | 16,384 칸 BFS ≈ 65,000 회 |
| 적 1 마리 부담 | 탐색 + 경로 저장 | 배열 읽기 1 회 |
| 적이 10 배 | 10 배 | **그대로** |
| DOTS 적합성 | 적마다 우선순위 큐·가변 길이 경로(`DynamicBuffer`) → 기획서 8.4 "컴포넌트 최소화" 위배 | 싱글턴 배열 1 개, 적에 붙는 컴포넌트 0 |

A\* 가 맞는 경우는 에이전트가 수십 마리 이하이고 각자 **다른 목적지**로 갈 때다. 이 게임은 정반대다.

**구현**

| 파일 | 내용 |
|---|---|
| `FlowField.cs` | 싱글턴 (방향 byte 배열 + 8 방향 표) |
| `FlowFieldBuilder.cs` | BFS **순수 함수** (테스트 대상) |
| `FlowFieldSystem.cs` | **플레이어가 다른 칸으로 넘어갔을 때만** 재계산, 단일 스레드 잡 |
| `EnemyChaseSystem.cs` | 추격 방향을 필드에서 가져옴. 2 u 이내는 직진(필드는 칸 단위라 코앞에서 떨린다) |

재계산 빈도: 1 u = 1 타일, 플레이어 속도 5 u/s → **초당 5 회 남짓**. BFS 는 메인 스레드를 막지 않게 잡으로 띄운다.

**중간에 잡은 버그 — 경로 규칙과 충돌 규칙의 불일치**

처음엔 BFS 의 대각선 금지 규칙을 "**양옆이 모두** 막혔을 때만" 으로 썼다 (모서리 뚫기를 막는 흔한 규칙).
그런데 이동 쪽(`TerrainMovement.SlideAlongWalls`)은 x·y 를 **따로** 시험하므로 **한쪽만 막혀도 그 축을 버린다.**
→ 필드가 "대각선으로 가라" 고 해도 적은 한 축으로만 움직여 경로를 벗어나고, 벽면을 따라 지그재그가 된다.

`PathAndCollisionAgreeOnEveryCell` 테스트(무작위 바위 배치에서 **모든 칸**의 필드 방향을 실제 충돌 규칙에
통과시켜 보는 테스트)가 이걸 잡았다. BFS 규칙을 "**한쪽이라도** 막히면 대각선 금지" 로 바꿔 두 규칙을 일치시켰다.

> **이게 이번 이슈에서 가장 값진 부분이다.** ISSUE-013 은 "경로를 못 찾는" 문제였는데,
> 고치는 과정에서 **"찾은 경로를 걷지 못하는"** 같은 계열의 버그를 새로 만들 뻔했다.
> 육안으로는 "적이 벽 근처에서 좀 이상하게 움직인다" 정도로만 보였을 것이다.

**테스트 14 개**

| 분류 | 검증 내용 |
|---|---|
| 기본 | 출발 칸은 방향 없음 / 빈 맵은 전 칸 도달 / **모든 칸에서 따라가면 플레이어에 닿음** / 바위 칸은 방향 없음 |
| 우회 | 벽을 **돌아가는** 경로가 나옴(직선보다 길어야 함) / **U 자 오목 함정 탈출** / 도달 불가 구역은 방향 없음 |
| 규칙 일치 | 모서리 대각선 통과 안 함 / **무작위 배치 전 칸에서 필드 방향 = 이동 가능 방향** |
| 방향 표 | 8 방향 전부 단위 길이(대각선이 √2 배 빨라지지 않게) / 반대 방향 계산 / 오프셋과 벡터 부호 일치 |
| 재사용 | 두 번째 필드가 첫 필드에 오염되지 않음 / 플레이어가 바위 안이어도 필드는 만듦(적 전체 정지 방지) |

**재발 방지**

- **"경로를 만드는 규칙" 과 "이동을 막는 규칙" 은 반드시 같아야 한다.** 둘이 어긋나면 유닛이
  "가라는 대로 갈 수 없는" 상태가 되고, 증상은 희미한데 원인은 두 파일에 나뉘어 있어 찾기 어렵다.
  두 규칙을 **교차 검증하는 테스트**(`PathAndCollisionAgreeOnEveryCell`)를 남겨 뒀다.
- **충돌 해소(collision response)와 경로 탐색(navigation)은 다른 문제다.** 덩어리 5 에서 축 분리
  미끄러짐으로 우회까지 된다고 본 것이 착오였다. 미끄러짐은 "벽에 닿았을 때 어떻게 되나" 만 정하고,
  "어디로 가야 하나" 는 답하지 않는다.

### ISSUE-014

| | |
|---|---|
| **발생일시** | 2026-09-18 (M3 덩어리 6 흐름장, 사용자 육안 검증 중 발견) |
| **마일스톤** | M3 |
| **분류** | 게임로직 |
| **상태** | ✅ 해결 |
| **해결일** | 2026-09-18 |
| **관련 작업** | [WorkLog 2026-09-18 (6) 흐름장](WorkLog.md) |

**증상**

> "중간에 바위가 없어도 오는 중에 바위 때문에 경로가 바뀌면 중간에 바위가 없어도
> 플레이어에게 다가오는 경로가 직선이 아닌 이상한 경로로 오고있어"

[ISSUE-013](#issue-013) 은 해결됐다(적이 벽에 끼이지 않는다). 그런데 **경로의 모양**이 부자연스럽다.
장애물이 없는 구간에서도 계단·L 자로 돌아온다.

**재현 조건**

항상. 바위가 하나도 없어도 나타난다 — 플레이어와 적을 잇는 선이 축이나 대각선에 정렬되지 않았을 때.

**원인**

두 가지가 겹쳤다.

**1) BFS 는 이동 비용을 전부 1 로 본다 — 대각선도 1**

그러면 거리 척도가 **체비쇼프 거리**가 되고, 이 척도에서는 **같은 비용의 경로가 무수히 많다.**
(0,0) → (10,3) 은 "대각선 3 회 + 직진 7 회" 를 어떤 순서로 섞어도 전부 10 걸음이다.

BFS 는 그중 **먼저 도달한 순서**로 아무거나 하나를 고정한다. 이웃을 도는 순서(0~7)가 곧 경로 모양이 된다.
한번 그렇게 굳은 칸을 밟은 적은 뻥 뚫린 곳에서도 그 길을 따라간다.

**즉 필드는 "몇 걸음인지" 는 맞지만 "어느 쪽인지" 가 부정확하다.**
최단 경로이긴 하나 **그리드 걸음 수 기준**이지 **실제 거리 기준**이 아니다.

**2) 방향이 8 개로 양자화되어 있다**

칸마다 방향 인덱스 0~7 하나만 저장하므로, 적은 8 방향으로만 움직인다.
예컨대 20° 방향으로 가야 할 때 0°(E)와 45°(NE)를 번갈아 밟아 계단이 된다.

**시도한 것**

| 시도 | 결과 |
|---|---|
| BFS + 방향 인덱스 (덩어리 6) | 🔄 우회 능력은 확보(ISSUE-013 해결), **경로 모양이 부자연스러움** |
| 팔각(octile) 거리 + 방향 인덱스 | ❌ 방향 오차 최대 20.4° — 기울기가 팔분면마다 상수라 22.5° 단위로 양자화 |
| 아이코널 1 차 (축 정렬 4 이웃) | ❌ 11.5° — 대각선 방향 오차가 큼 |
| **아이코널 + 대각선 스텐실** | ✅ 8° 미만 |

**해결**

**거리 필드 + 기울기.** 방향 인덱스를 버리고 칸마다 **플레이어까지의 거리**를 저장한 뒤,
적이 이웃 네 칸의 거리로 **기울기**를 구해 그 반대로 간다. 방향이 연속값이라 8 방향 양자화가 사라진다.

**여기서 두 번 더 틀렸다 — 척도가 문제였다**

| 척도 | 대각선 비용 | 빈 지형에서의 방향 오차 (실측 최대) | 판정 |
|---|---|---|---|
| 체비쇼프 (BFS) | 1 | — (경로 자체가 계단) | ❌ 최초 구현 |
| 팔각(octile) | √2 | **20.4°** | ❌ 기울기가 팔분면마다 상수라 22.5° 단위로 양자화된다 |
| 아이코널 1 차 (4 이웃) | — | **11.5°** | ❌ 나아졌지만 대각선 방향 오차가 크다 |
| **아이코널 + 대각선 스텐실 (8 이웃)** | — | **8° 미만** | ✅ 채택 |

핵심 교훈: **"대각선을 √2 로 고치면 되겠지" 가 틀렸다.** 팔각 거리의 기울기는
팔분면 안에서 **상수 벡터**라(예: |dx|>|dy| 구간에서 항상 (1, 0.414)) 실제 각도와 무관하게
22.5° 단위로 끊긴다. 계단이 각도만 바뀌어 남는다.

아이코널 방정식(|∇D| = 1)을 풀면 **진짜 유클리드 거리**에 수렴해 필드가 매끈한 원뿔이 되고,
기울기가 플레이어를 정확히 가리킨다. 다만 1 차 축 정렬 스텐실만 쓰면 오차가 **대각선 방향에서 최대**라
(11.5°) 45° 돌아간 **대각선 스텐실**을 추가해 둘의 최솟값을 취했다 — 서로 약한 구간이 반대라 이방성이 상쇄된다.

**풀이 방법**: 우선순위 큐(다익스트라·FMM) 대신 **래스터 스윕(fast sweeping)**.
큐도 방문 표시도 없어 추가 메모리가 0 이고, 배열을 순서대로 훑어 캐시 지역성이 좋다.
스윕 방향 4 가지를 값이 줄지 않을 때까지 반복한다 (테스트로 수렴 횟수 확인).

**덤으로 잡은 것 — 안장점**

좌우 우회로가 똑같이 좋은 자리(대칭인 U 자 바위 등)에서는 중앙 차분이 양쪽에서 상쇄되어
**기울기가 0 이 된다.** 적이 "어디로 갈지 모르는" 상태로 멈춘다.
거리 필드에는 출발점 말고 지역 최소가 없으므로 **더 작은 이웃이 반드시 존재한다** —
이산 최급강하로 되돌아가 한쪽을 고르게 했다. `EscapesConcaveTrap` 테스트가 이걸 잡았다.

**테스트 (총 16 개)**

| 분류 | 검증 내용 |
|---|---|
| 기본 | 출발 거리 0 / 빈 맵 전 칸 도달 / 바위는 도달 불가 / 밀폐 구역은 방향 없음 |
| 척도 | 직교 이웃 = 1 / **유클리드 거리와 ±9% 이내** |
| **경로 모양** | **빈 지형에서 방향 오차 8° 미만** / 걸어간 거리가 직선의 1.15 배 이내 |
| 우회 | 벽을 돌아감 / **U 자 함정 탈출**(안장점 처리) |
| 규칙 일치 | 모서리 대각선 통과 안 함 / **무작위 배치 전 칸에서 한 걸음은 반드시 나아가고, 플레이어에 가까워짐** |

**재발 방지**

- **"경로가 맞다" 와 "경로가 자연스럽다" 는 다른 문제다.** BFS 경로는 최단이었지만(걸음 수 기준)
  보기에 이상했다. 최적성만 테스트하면 이 결함을 못 잡는다 — **방향 오차 각도를 직접 재는 테스트**를 남겨 뒀다
  (`OpenTerrainDirectionPointsStraightAtSource`).
- 격자 위에서 경로를 만들 때는 **어떤 거리 척도를 쓰고 있는지**를 먼저 의식한다.
  체비쇼프·맨해튼·팔각은 전부 "격자에서 자연스러워 보이지만" 실제 유클리드와 다르고,
  그 차이가 곧 경로의 모양이 된다.
- 대칭인 지형에서는 **기울기가 0 이 되는 자리가 반드시 생긴다.** 연속적인 필드를 쓸 때는
  이산 폴백을 함께 둔다.
